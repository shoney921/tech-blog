# Shoney Tech Blog

VitePress 개인 기술 블로그. 사이트는 `https://blog.shoneylife.com`이며 Cloudflare Pages가 `main` 푸시 시 자동 배포한다. 프로젝트 작업 규칙은 `CLAUDE.md`를 따른다.

이번 애드센스 작업은 **로컬 승인 준비물**이다. 피처 브랜치에만 커밋하며 main 머지·푸시·배포·계정 신청은 하지 않는다. 개인정보 처리방침과 문의 페이지의 자리표시를 채우기 전에는 승인 신청 준비가 끝난 것으로 보지 않는다.

## 확인된 게시자 정보와 남은 순서

운영자가 제공한 코드의 게시자 ID는 `pub-6054380963868861`이다. `docs/.vitepress/adsense.config.json`에 저장했으며 **enabled는 false**다. `docs/public/ads.txt`에는 이 ID와 Google 공식 형식으로 구성한 DIRECT 레코드를 넣었다. 계정의 ads.txt 스니펫과 최종 대조는 아직 하지 않았다.

나중에 공개 반영이 허용되면 `adsense.config.json`의 `enabled`를 `true`로 바꾸거나 빌드 환경의 `ADSENSE_PUBLISHER_ID`를 실제 ID로 설정한다. 이번 단계는 로컬 반영까지만 한다. 문의 이메일 및 처리방침의 미정 항목도 아직 확정해야 한다.

애드센스 화면의 “코드를 삽입했습니다”는 공개 HTML에 코드가 올라갔다는 확인이다. 로컬 빌드 성공만으로 체크하거나 연결 확인을 완료했다고 간주하지 않는다. 신청 대상은 `shoneylife.com`, 이 저장소의 배포 대상은 `blog.shoneylife.com`이므로 루트 도메인 연결 방식도 확인해야 한다. 루트 ads.txt에 동일 판매자 행을 제공하거나, 서로 다른 판매자 설정이 필요하면 루트 파일에서 `subdomain=blog.shoneylife.com`으로 위임하는 방법을 검토한다. 현재 저장소에 루트 도메인의 설정을 임의로 추가하지 않는다. [Google ads.txt FAQ](https://support.google.com/adsense/answer/9785052?hl=ko).

## 사람이 채울 값

우선 운영자가 할 일은 아래 두 가지다. 확인된 공개 정보만 전달하면 파일 반영과 빌드 검증은 에이전트가 처리할 수 있다.

1. 블로그에 공개할 문의 이메일 주소를 정한다. 이메일 수신 여부는 운영자가 직접 확인한다.
2. [애드센스](https://www.google.com/adsense/start/)에 직접 가입 또는 로그인해 사이트 추가를 진행하고, 화면에 표시되는 게시자 ID(`pub-`로 시작)와 ads.txt 한 줄을 확인한다. 블로그 주소는 `https://blog.shoneylife.com`이다. 입력란에서 루트 도메인만 받는다면 `shoneylife.com` 기준 안내를 따르고 하위 도메인의 연결·ads.txt 탐색도 확인한다. 비밀번호, 인증 코드, 결제 정보는 공유하지 않는다.

공개 정보가 준비되면 에이전트가 연락처·ID·ads.txt 반영, 처리방침의 미정 항목 점검, 로컬 검증까지 진행할 수 있다. 로그 보관 설정과 광고 파트너 등 계정 안에서만 확인 가능한 사실은 운영자가 확인해야 한다. 그 뒤 배포가 별도로 허용되면 에이전트가 병합·배포·공개 URL 확인을 진행할 수 있다. 현재는 배포하지 않는다. 공개 확인이 끝난 다음 운영자가 애드센스 화면에서 **연결 확인 → 검토 요청**을 진행한다. [Google 공식 연결 절차](https://support.google.com/adsense/answer/7584263?hl=ko).

- `docs/contact.md`, `docs/privacy.md`: 실제로 수신 가능한 공개 문의 이메일. 주소 결정 후 실제 링크로 바꾸고 수신 확인.
- `docs/privacy.md`: 시행일, 문의 자료 보관 기간·삭제 절차, Cloudflare 로그 설정·열람 범위·보관 기간. 실제 운영 및 적용되는 개인정보 요건에 맞게 확정.
- `docs/privacy.md`: 광고 활성화 시 사용하는 Google 외 광고 공급업체·네트워크의 실제 목록과 개인정보·거부 설정 링크. 사용하지 않으면 그 사실을 명시.
- 빌드 환경 `ADSENSE_PUBLISHER_ID`: 본인 계정의 `pub-`와 숫자 16자리. ID는 공개 식별자이며 비밀번호/API 키가 아니다. 계정 로그인과 값 입력은 운영자가 직접 진행.
- `docs/public/ads.txt`: 계정에서 복사한 실제 판매자 레코드. 스크립트 ID와 일치 여부 확인.
- 승인 후: 광고 단위 ID, 광고 위치·크기, 자동 광고 사용 여부, 지역별 동의 관리/CMP 설정. 현재는 광고 단위와 CMP를 구현하지 않았다.

## 로컬 빌드와 광고 스위치

```sh
pnpm install
# 명시적으로 끈 상태. 기본적으로 환경 변수가 없어도 꺼진다.
ADSENSE_PUBLISHER_ID= pnpm docs:build
pnpm docs:preview
```

설정 변경 후에는 `pnpm check:adsense`로 켜짐·잘못된 ID·꺼짐을 자동 검증할 수 있다. 설정된 공개 게시자 ID로 로컬 HTML만 검사하며 Google 광고 서버에 접속하지 않는다. 마지막에는 꺼짐 빌드로 복원하고, 안내 페이지·링크 및 ads.txt 복사도 검사한다. 검증 중에는 같은 폴더에서 다른 빌드나 미리보기를 동시에 실행하지 않는다.

`docs/.vitepress/config.mts`는 `adsense.config.json`과 프로세스 환경 변수를 읽으며 `.env` 파일을 자동으로 읽지 않는다. 환경 변수 `ADSENSE_PUBLISHER_ID`가 있으면 빈 값도 설정 파일보다 우선한다. 환경 변수가 없으면 설정 파일의 enabled가 true일 때만 저장된 ID를 사용한다. 기본값은 false이며, 최종 ID가 없거나 공백이면 광고 head 항목은 빈 배열이다. 값이 있으면 형식을 검증하고 `async`, `crossorigin="anonymous"`인 공식 로더를 head에 한 번 삽입한다. 잘못된 값이면 빌드를 실패시켜 배포를 막는다. 설정 파일에는 운영자가 제공한 실제 공개 ID만 기록하며 임의의 ID를 넣지 않는다.

실제 ID를 사용할 때는 운영자가 로컬 셸 또는 Cloudflare Pages의 **빌드 환경 변수**에 `ADSENSE_PUBLISHER_ID`를 설정한 뒤 새로 빌드한다. 설정 해제도 재빌드가 필요하다. 기존 정적 결과물이 자동으로 바뀌지 않는다. 확인용 로더는 자동 광고에서도 사용하는 코드이므로, 승인 후 계정의 자동 광고가 켜져 있으면 별도 광고 단위 없이도 광고가 나올 수 있다. 확인만 할 때는 계정의 자동 광고 설정도 확인한다.

기본 빌드 후 `docs/.vitepress/dist`의 HTML·JS에서 `adsbygoogle`, `pagead2.googlesyndication.com`, `ca-pub-`가 없는지 확인한다. 활성화 빌드는 생성 HTML head에서 로더 1개와 정확한 client ID·async·crossorigin을 확인한다. 로컬 검증에서는 외부 광고 요청을 차단하고 실제 광고를 클릭하지 않는다. 검증을 마친 뒤 꺼진 상태로 다시 빌드한다.

## ads.txt 자리

VitePress의 public 디렉터리는 루트 `public/`이 아닌 `docs/public/`이다. `docs/public/ads.txt`가 빌드 결과 루트의 `/ads.txt`로 그대로 복사된다. 처음에는 주석만 남겼으며, 현재는 운영자가 제공한 게시자 ID로 Google 공식 형식의 판매자 레코드를 작성했다. ads.txt 자체는 광고 스크립트를 실행하지 않는다. 실제 계정의 스니펫과 대조 및 공개 URL에서의 수집 확인은 남아 있다. 파일을 로컬에 작성했다고 Google의 판매자 인증이 완료된 것은 아니다.

계정에서 제공하는 ads.txt 행을 그대로 복사한다(광고 시스템 도메인, 실제 게시자 ID, 관계 유형, 인증기관 ID). 숫자 예제를 그대로 쓰지 않는다. 환경 변수로 ads.txt가 자동 생성되지는 않는다. 이후 배포가 별도로 승인되면 `/ads.txt`가 HTTP 200과 텍스트 본문으로 제공되는지, SPA HTML이나 리디렉션 오류가 아닌지 확인한다. 서브도메인 `blog.shoneylife.com`과 루트 `shoneylife.com`의 탐색·위임 설정도 계정 안내에 따라 확인한다. 이 저장소만으로 루트 도메인의 설정을 바꿀 수는 없다. [Google ads.txt 가이드](https://support.google.com/adsense/answer/12171612?hl=ko), [IAB ads.txt 사양](https://iabtechlab.com/ads-txt/).

## 애드센스 승인 체크리스트

ads.txt의 레코드와 스크립트의 게시자 ID가 같은지 확인하고, 실제 계정의 안내와 최종 대조한다.

### 콘텐츠와 사이트 상태

- [ ] 소개·문의·개인정보 처리방침의 미정 항목을 모두 채우고 실제 서비스와 일치하는지 확인.
- [ ] 글 수를 승인 보장 조건으로 삼지 않기. 최소 글 수·글자 수·방문자 수에 관해 이 작업에서 확정한 공식 수치는 없다. **공식 문서 확인 필요**.
- [ ] 주요 카테고리와 연재가 독립적으로 읽을 만한 설명, 실행 경험, 검증 가능한 예시를 제공하는지 검토. 책·문서 요약만 반복하거나 출처 없이 복제한 콘텐츠, 자동 생성 문장의 나열이 아닌지 점검.
- [ ] 가치 낮은 콘텐츠 반려에 대비해 글마다 독자가 얻는 정보와 고유한 기여를 확인. 빈 페이지, 미완성 글, 중복 글, 과도하게 짧은 내용, 깨진 링크, 이미지·코드의 이용 권한 점검. 이번 작업은 기존 글을 수정하거나 전수 심사하지 않는다.
- [ ] 모바일에서 메뉴·글·안내 페이지가 읽히고 검색과 카테고리 이동이 동작하는지 확인. 로그인 없이 본문에 접근 가능한지 점검.
- [ ] 실제 배포 시 robots.txt, sitemap.xml, HTTP 상태, Cloudflare 접근 제한이 심사 크롤러를 막지 않는지 확인.

[Google 사이트 준비 안내](https://support.google.com/adsense/answer/7299563?hl=ko)와 [미승인 사유 안내](https://support.google.com/adsense/answer/81904?hl=ko)를 기준으로 검토한다. 안내 페이지를 만드는 것만으로 승인이 보장되지는 않는다.

### 신청 순서 — 운영자가 나중에 직접 진행

1. 위 체크리스트와 사람이 채울 값을 완료한다. 개인정보 문구는 [Google 필수 콘텐츠](https://support.google.com/adsense/answer/1348695?hl=ko) 및 실제 처리 방식에 맞춰 확정한다.
2. 운영자가 직접 계정 요건을 확인하고 사이트를 추가한다. 로그인·본인 확인·결제 정보 등은 이 작업의 범위가 아니다.
3. 계정에서 제공하는 ID와 ads.txt 레코드를 사용하고 연결 방법을 선택한다. 이 저장소는 head 스크립트 방식의 자리를 제공한다. Google은 다른 연결 방법도 안내한다.
4. 지역별 동의 요건을 확인한다. EEA·영국·스위스 사용자에게 개인 맞춤 광고를 제공할 때는 인증 CMP 요건을 검토한다. 개인정보 페이지가 동의 수단을 대신하지 않는다. [Google 동의 관리 요건](https://support.google.com/adsense/answer/13554116?hl=ko).
5. 로컬 검증 후 **별도로 배포 승인을 받은 경우에만** 공개한다. 실제 URL에서 연락처·head·ads.txt·접근성을 확인한 뒤 계정에서 연결 확인과 검토 요청을 한다. 로컬 파일만으로는 Google 심사가 이루어지지 않는다.
6. 계정에서 상태를 확인하고 반려되면 제시된 원인을 수정해 다시 검토 요청한다. 심사 기간·ads.txt 반영 시간은 **신청 시점의 공식 문서 확인 필요**, 기한을 보장하지 않는다. [사이트 연결 절차](https://support.google.com/adsense/answer/7584263?hl=ko).

### 승인 후 광고 위치와 성능

현재는 확인용 head 설정만 있고 광고 슬롯은 없다. 승인 후 먼저 본문 하단 등 읽기를 방해하지 않는 위치에 하나의 수동 광고 단위를 검토한다. 실제 슬롯 ID를 별도 Vue 컴포넌트에 넣고 `theme/index.ts`의 글 전용 슬롯에서 사용한다. 소개·문의·개인정보 페이지에는 광고 슬롯을 만들지 않는다. 로더를 컴포넌트마다 중복 삽입하지 않고, VitePress SPA 이동 시 마운트된 새 슬롯에 한 번만 초기화하며 이미 채워진 슬롯을 재초기화하지 않는다.

로더는 비동기지만 네트워크와 메인 스레드 비용이 없어지는 것은 아니다. 첫 화면의 제목·본문·대표 이미지 로드를 우선하고, 초기에는 첫 화면 광고와 자동 광고를 피하는 운영안을 권한다. 실제 광고 코드와 허용 형식은 계정에서 복사하고 임의로 변형하지 않는다.

광고가 들어올 공간은 **응답 전에 CSS로 확보**한다. 선택한 광고 형식에 맞춰 모바일·데스크톱별 너비와 최소 높이를 정하고, 늦게 광고가 오거나 미송출되어도 보이는 영역을 갑자기 접지 않는다. 반응형 광고가 예약 공간을 넘지 않는지 실제 크기로 확인한다. 구체적인 픽셀 값은 슬롯을 선택한 뒤 결정하며 현재는 빈 광고 여백도 만들지 않는다. [Google의 광고 레이아웃 이동 설명](https://developers.google.com/publisher-tag/guides/minimize-layout-shift)은 공간 확보 원칙의 참고 자료이며, GPT API를 애드센스 구현에 그대로 넣는 안내는 아니다.

광고 전후 같은 기기·네트워크 조건에서 Lighthouse/DevTools로 LCP·CLS를 비교한다. 느린 네트워크, 광고 차단, 미송출, 화면 회전, SPA 이동, 동의 거부도 확인한다. 실제 광고·CMP가 없는 지금 단계에서는 광고 활성화 후 성능이나 CLS를 보장할 수 없다.

- 실제 계정과 무관한 임시 형식 테스트 값을 빌드 프로세스에만 전달해 켜짐 빌드 검증. HTML 118개 모두 head에 정확히 하나의 async 로더와 예상 client·crossorigin 속성 확인. 테스트 값은 소스·ads.txt에 저장하지 않았으며 이후 기본 꺼짐 빌드로 복원.
- 잘못된 ID 형식으로 빌드가 실패하는 것 확인.
- 로컬 preview와 Chromium에서 375px·1280px 화면으로 세 안내 페이지의 제목·푸터 링크·내비게이션 이동·가로 넘침 없음 확인. 외부 요청은 차단.
- 로컬 `/ads.txt` HTTP 200, `text/plain`, 원본과 동일한 주석 전용 본문 확인.
- 빌드에 500 kB 초과 청크 경고가 있으나 오류는 없음.
- 미확인: 실제 Google 계정 연결·승인, 운영 도메인 및 루트 도메인의 ads.txt 수집, 실제 광고/CMP 동작·성능, 개인정보 문구의 최종 적합성, 기존 글 전체의 승인 적합성. 공개 배포와 푸시는 하지 않음.

### 실제 게시자 ID 반영 후 확인

운영자가 제공한 실제 ID로 켜짐 빌드의 HTML 118개 head를 검증했고, 마지막에 꺼짐으로 복원한 HTML·JS 358개에서 광고 코드가 없음을 확인했다. ads.txt가 설정 파일의 실제 ID와 일치하는지도 검사했다. 공개 배포·계정의 연결 확인·검토 요청은 수행하지 않았다. 초기의 주석 전용 ads.txt 검증 기록은 당시 상태에 대한 기록이다.

공개 URL의 읽기 확인을 시도했으나 이 실행 환경에서는 `shoneylife.com`의 DNS 조회가 실패하고 `blog.shoneylife.com`은 HTTP 403을 반환했다. 공개 HTML 및 루트 ads.txt는 확인하지 못했다. 이 결과만으로 Google 크롤러의 접근 가능 여부를 판단하지 않는다. 실제 브라우저와 DNS·Cloudflare 설정에서 별도 확인이 필요하다.
