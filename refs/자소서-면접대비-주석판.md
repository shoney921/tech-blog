# 1부. [비정형 대화 서비스를 다중 사용자 프로덕션 시스템으로 전환]

## 1-1. 도입 문단

> **원문**
> 기존 Custom GPTs로 운영되던 대화형 진단 서비스를 다수 사용자가 이용하는 프로덕션 웹 앱('CEO AX Diagnosis Assistant')으로 재구현하는 과제를 수행했습니다. 목적은 비정형 대화 흐름의 구조화와 LLM 품질 및 운영 안정성의 동시 확보였습니다.

**등장 키워드**: Custom GPTs · 비정형 대화 흐름의 구조화 · 프로덕션 전환

### Custom GPTs
OpenAI ChatGPT 안에서 시스템 프롬프트 + 지식파일(최대 20개) + Actions(외부 API 호출)를 묶어 만드는 **노코드 챗봇 패키지**. 계정이 ChatGPT Plus/Team이어야 쓸 수 있고, 대화 상태는 OpenAI가 관리하며, 로그·DB·인증을 개발자가 소유하지 못한다.

**프로덕션 전환이 필요했던 이유 — 면접에서 이 4개만 말하면 충분하다**

| 한계 | 프로덕션에서 왜 문제인가 |
|---|---|
| 데이터 소유권 없음 | 진단 응답을 DB에 못 쌓음 → 통계·후속 분석 불가 |
| 흐름 비결정성 | 같은 사용자가 같은 답을 해도 다음 질문이 달라짐 → 진단 결과 신뢰도 붕괴 |
| 인증·과금 통제 불가 | 사내 사용자만 허용, 사용량 제한 같은 정책을 걸 수 없음 |
| 관측 불가 | 어디서 실패했는지 로그가 없음 → 장애 대응 불가 |

**대체 선택지 비교** (왜 굳이 직접 만들었나에 대한 방어)

| 선택지 | 특징 | 왜 안 골랐나(뼈대) |
|---|---|---|
| Custom GPTs 유지 + Actions | 가장 빠름 | 위 4가지 한계 그대로 |
| Azure OpenAI Assistants API | 스레드/상태를 플랫폼이 관리, 파일검색 내장 | 흐름 결정성이 여전히 모델 판단에 의존, 프리뷰 단계 변동성 |
| Copilot Studio / Power Virtual Agents | 엔터프라이즈 노코드, MS 거버넌스 | 커스텀 진단 로직·산출물 생성 자유도 부족 |
| Dify / Flowise / LangFlow | 오픈소스 GUI 오케스트레이터 | 운영 주체가 우리가 되어야 하는 건 동일한데 디버깅 스택만 깊어짐 |
| **직접 구현(선택)** | FSM + LLM 분리 | 결정성·감사성·장애격리를 전부 우리가 통제 |

**예상 질문**
- **Q. Custom GPTs로 이미 되던 걸 왜 몇 달 들여 다시 만들었나요? ROI는?**
  → "단일 사용자 데모와 다중 사용자 서비스는 요구사항이 다릅니다. ①진단 결과를 DB에 축적해야 후속 컨설팅이 가능했고 ②동일 입력에 동일 흐름이 보장돼야 진단이라는 이름을 붙일 수 있었으며 ③사내 사용자 통제와 장애 시 대응이 필요했습니다. 셋 다 플랫폼 밖에선 불가능한 요구였습니다."
- **Q. '비정형 대화 흐름의 구조화'를 한 문장으로 정의하면?**
  → "자유 대화를 **단계(state) × 슬롯(수집해야 할 정보) × 전이조건**의 3요소로 환원한 겁니다. LLM은 그 안에서 문장만 생성합니다."
- **Q. 사용자 수는 몇 명이었나요? 실제 프로덕션 트래픽인가요?**
  → 숫자 준비 필요. (동시 20명 부하 기준 / 총 사용자 수 / 운영 기간 — 부록 B 참조)

## 1-2. 역할과 스택 문단

> **원문**
> 요구사항 분석부터 아키텍처 설계, 풀스택 개발 및 운영까지 전 주기를 주도한 핵심 개발자로 참여해 대화 상태기계 엔진, LLM 연동 레이어, 데이터 파이프라인 설계를 담당했습니다. 백엔드는 FastAPI(async SQLAlchemy)와 프론트엔드는 React를 활용하고, LLM은 Azure OpenAI를, 인프라는 Docker/PostgreSQL로 구축했습니다. 또한 Neo4j 기반 GraphRAG와 Elasticsearch 기반 하이브리드 검색 파이프라인을 구축한 경험이 있습니다.

**등장 키워드**: FastAPI · async SQLAlchemy · React · Azure OpenAI · Docker · PostgreSQL · Neo4j GraphRAG · Elasticsearch 하이브리드 검색

### FastAPI
Python ASGI 웹 프레임워크. Starlette(웹) + Pydantic(검증) 조합. 타입 힌트 기반 자동 검증·OpenAPI 문서 생성이 핵심 가치.

**LLM 서비스에서 FastAPI를 쓰는 진짜 이유**: LLM 호출은 CPU가 아니라 **네트워크 대기(I/O bound)** 다. 한 요청이 5초 대기하는 동안 이벤트 루프가 다른 요청을 처리할 수 있어야 동시 사용자를 받는다. 동기 프레임워크였다면 워커 수만큼만 동시 처리된다.

> **주의(자주 나오는 함정)**: FastAPI에서 `def`(비동기 아님)로 선언한 엔드포인트는 threadpool에서 돌고, `async def` 안에서 동기 블로킹 호출(예: `requests.get`, 동기 DB 드라이버)을 하면 **이벤트 루프 전체가 멈춘다**. "async를 썼는데 왜 안 빨라졌나요?"의 90%가 이것.

| 대체 기술 | 특징 | 비교 포인트 |
|---|---|---|
| **Spring Boot (WebFlux)** | 내 원래 주력. Reactor 기반 논블로킹 | "백엔드 8년인데 왜 Java 안 쓰고 Python?" → LLM 생태계(LangChain, 임베딩, 토크나이저)가 Python 우선 |
| **Django + DRF** | 배터리 포함, ORM/Admin 강력 | 관리화면 빨리 필요하면 유리, async 지원은 후발 |
| **Flask / Quart** | 가벼움 | 검증·문서화 직접 붙여야 함 |
| **Node.js (NestJS)** | I/O 비동기 기본, 프론트와 언어 통일 | 스트리밍 SSE 처리엔 강함 |
| **LiteLLM Proxy / Gateway** | LLM 호출 전용 게이트웨이(라우팅·폴백·쿼터) | **"모델 스위처를 직접 만들었다"의 대체제** — 질문 나올 수 있음 |

### async SQLAlchemy
SQLAlchemy 2.0의 `AsyncSession` + `asyncpg` 드라이버 조합.

**알아야 할 것 (되물음 대비)**
- **커넥션 풀**: `pool_size`(상시), `max_overflow`(버스트 허용), `pool_timeout`, `pool_recycle`. 자소서 3부에 "DB 커넥션 풀 튜닝"을 썼으므로 **실제 숫자를 기억해야 한다.**
- **lazy loading 금지**: async 컨텍스트에서 관계 지연로딩은 `MissingGreenlet` 에러. `selectinload`/`joinedload`로 명시적 eager loading.
- **N+1 문제**: 리스트 조회 시 관계마다 추가 쿼리. `selectinload`로 해결.
- **Alembic**: 마이그레이션 도구. "스키마 변경 관리 어떻게 했나요?"에 대한 답.

| 대체 | 특징 |
|---|---|
| **SQLModel** | FastAPI 제작자가 만든 SQLAlchemy+Pydantic 래퍼. 보일러플레이트 감소 |
| **Tortoise ORM / Piccolo** | async 네이티브 ORM. 생태계는 얇음 |
| **raw asyncpg** | 가장 빠름. 복잡 쿼리는 오히려 명확 |
| **Prisma Python** | 스키마 우선. 타입 안정성 좋음 |

### PostgreSQL
**왜 Postgres였나**에 대한 답 3종: ①JSONB로 LLM 응답 원문을 스키마 변경 없이 저장 ②`pgvector` 확장으로 벡터 검색까지 한 DB에서 가능 ③트랜잭션·제약조건이 진단 데이터 정합성에 필요.

| 대체 | 비교 |
|---|---|
| MySQL/MariaDB | JSON 지원 약함, 벡터 확장 미성숙 |
| MongoDB | 스키마리스는 편하나 진단 이력의 정합성 보장이 약함 |
| **pgvector vs 전용 벡터DB** | 데이터 100만건 이하 + 메타데이터 필터 많으면 pgvector가 운영 부담 적음. 그 이상이면 Qdrant/Milvus |

## 1-3. 상태기계 · Envelope · Probe · 폴백 문단 ★핵심

> **원문**
> 진단 엔진을 '결정적 상태기계'로 두고 LLM을 '콘텐츠 생성 레이어'로 분리했습니다. 매 턴 구조화된 Envelope(메시지, 동적 선택지, 단계 상태, 슬롯 평가)를 생성하고, 답변이 빈약할 경우 부족한 축만 재질의하는 Probe 로직을 구현했습니다. 아울러 'LLM 우선 + 실패 시 규칙 기반 폴백'을 적용해 외부 의존성 장애가 전체 흐름을 끊지 않도록 방어벽을 설계했습니다.

**등장 키워드**: 결정적 상태기계 · 콘텐츠 생성 레이어 분리 · Envelope · 동적 선택지 · 슬롯 평가 · Probe · LLM 우선 + 규칙 폴백

> 이 문단이 **자소서 전체에서 기술적으로 가장 좋은 부분**이다. 여기서 시간을 벌어야 한다.

### 결정적 상태기계 (Deterministic FSM)
업계 표준 용어로는 **Finite State Machine**, 대화 도메인에서는 **Dialogue Manager** 또는 **Orchestration Layer**.

구성 요소 4개 — 이 단어로 설명하면 바로 통한다:
- **State(상태)**: 진단의 각 단계
- **Slot(슬롯)**: 그 단계에서 채워야 하는 정보 항목
- **Transition(전이)**: 슬롯이 충족되면 다음 상태로
- **Guard(가드)**: 전이 조건 (예: 필수 슬롯 3개 중 3개 충족)

**"결정적"이 주는 이득 3가지 (외워서 말할 것)**
1. **재현성** — 같은 입력 → 같은 경로. 테스트 케이스를 쓸 수 있다.
2. **감사 가능성** — 어느 단계에서 무엇을 물었는지 로그로 추적. 금융권에서 특히 중요(4부와 연결).
3. **장애 격리** — LLM이 죽어도 흐름 자체는 산다.

#### 대체 기술 비교 ★"왜 LangGraph 안 썼냐"는 거의 확실히 나온다

| 기술 | 무엇인가 | 내 구현 대비 |
|---|---|---|
| **LangGraph** | 그래프 기반 상태머신. Checkpointer로 상태 영속화, HITL 인터럽트, 스트리밍, 타임트래블 디버깅 내장 | 가장 직접적 대체제. **1순위 질문** |
| **LangChain (LCEL)** | 체인 조합. 상태관리 약함 | 단발성 체인엔 충분, 다단계 대화엔 부족 |
| **LlamaIndex Workflows** | 이벤트 드리븐 워크플로우 | RAG 파이프라인 쪽에 강점 |
| **Semantic Kernel / MS Agent Framework** | MS 진영, Azure·.NET 친화 | Azure를 썼으므로 "검토했냐" 질문 가능 |
| **AutoGen / CrewAI** | 멀티에이전트 역할분담 | 고정된 진단 흐름엔 과설계 |
| **Temporal / AWS Step Functions / Azure Durable Functions** | 범용 durable workflow. 재시도·보상 트랜잭션의 정석 | 상태 영속·장기실행이 진짜 요구였다면 정답에 가까움 |
| **transitions (Python) / XState (JS)** | 순수 FSM 라이브러리 | 내가 만든 것과 같은 층위. "라이브러리도 있는데?" |
| **Rasa** | 전통 대화 NLU + 룰/스토리, 온프렘 | 폐쇄망 챗봇이면 여전히 유효 |

> **모범 답변 뼈대**
> "LangGraph를 검토했습니다. 다만 ①진단 흐름이 사전 정의된 고정 순서였고 그래프 추상화가 주는 이득이 크지 않았습니다 ②당시 프레임워크 버전 변동성이 커서 프로덕션 의존성으로 삼기 부담이었습니다 ③장애 분석 시 스택이 얕은 편이 유리했습니다. 다만 지금 재설계한다면 Checkpointer로 대화 상태를 영속화하고 HITL 인터럽트를 붙일 수 있다는 점 때문에 LangGraph를 진지하게 검토할 겁니다."
>
> **금기**: "몰라서 안 썼습니다"도, "직접 만든 게 더 낫습니다"도 안 된다. **트레이드오프로 설명**할 것.

### Envelope (구조화 출력)
매 턴 LLM이 반환하는 고정 스키마 객체. 자소서 기준 4필드: `메시지 / 동적 선택지 / 단계 상태 / 슬롯 평가`.

업계 표준 용어는 **Structured Output**. 구현 방식이 4가지이고, **어느 걸 썼는지 반드시 정리해둬야 한다**:

| 방식 | 보장 수준 | 설명 |
|---|---|---|
| **프롬프트로 요청 + 파싱** | 낮음 | "JSON으로 답해줘". 깨지면 재시도. 가장 흔한 실제 구현 |
| **JSON mode** (`response_format={"type":"json_object"}`) | 중간 | 유효한 JSON임은 보장, **스키마 일치는 미보장** |
| **Structured Outputs** (`json_schema`, `strict: true`) | 높음 | 지정 스키마 100% 준수. Azure OpenAI는 `2024-08-01-preview` 이후 지원 |
| **Function/Tool Calling** | 높음 | 함수 인자로 스키마 강제. 원래 용도는 도구 호출 |

**주변 라이브러리**
- **Instructor** — Pydantic 모델로 응답 강제 + 검증 실패 시 자동 재질의. 가장 실무적
- **Outlines / guidance** — 디코딩 단계에서 문법 제약(Constrained Decoding). 오픈모델용
- **Guardrails AI** — 출력 검증·교정 파이프라인
- **Pydantic** — 최소한 이건 썼다고 말할 수 있어야 함

**예상 질문**
- **Q. Structured Outputs 쓰셨나요, 아니면 파싱하셨나요?** → 정직하게 답하되, 안 썼다면 "당시 API 버전에서 미지원이었다 / 지금이면 strict 스키마를 쓸 것" 로 마감.
- **Q. 스키마 검증 실패율은 얼마였나요? 실패하면 어떻게 했나요?** → 재시도 횟수, 재시도 시 프롬프트를 바꿨는지(에러 메시지를 되먹임했는지), 최종 실패 시 폴백 경로.
- **Q. 스키마가 바뀌면 이전 대화 이력은 어떻게 처리하나요?** → 버저닝 이야기. (`envelope_version` 필드 + 마이그레이션)

### 동적 선택지 (Dynamic Choices / Suggested Replies)
LLM이 매 턴 선택지를 생성 → 사용자는 자유 입력 대신 클릭.

**설계 의도로 말할 것**: 자유 입력을 줄이면 ①슬롯 채우기가 안정적이고 ②프롬프트 인젝션 표면이 줄고 ③입력 부담이 낮아져 완주율이 오른다. 대신 **선택지 자체가 사용자를 유도(anchoring)하는 편향**이 생기므로 "기타/직접입력"을 반드시 남긴다 — 이 트레이드오프까지 말하면 점수가 오른다.

### 슬롯 평가 (Slot Filling) + Probe (Clarification Question)
- **Slot Filling**: 대화에서 필요한 정보 항목(슬롯)을 채워가는 전통 대화시스템 개념. Rasa·Dialogflow의 기본 메커니즘.
- **Probe/Elicitation**: 슬롯이 비었거나 답변이 빈약할 때 **부족한 축만 골라 되묻는** 것. 자소서 표현 그대로 "부족한 축만 재질의".

**반드시 정리해둘 것 — 판단 주체가 누구인가**

| 방식 | 장점 | 단점 |
|---|---|---|
| **LLM이 슬롯 충족 여부 평가** | 뉘앙스 포착, 유연 | 비결정적, 평가 자체가 환각 가능 |
| **규칙 기반(길이·키워드·정규식)** | 결정적, 빠름, 무료 | 형식만 갖춘 무의미 답변 통과 |
| **하이브리드(권장)** | 규칙으로 1차 컷 → 애매한 것만 LLM 판정 | 구현 복잡 |

**무한 Probe 방지 장치**를 물어볼 가능성이 높다 → "재질의 최대 N회 제한 후 부분 정보로 진행" 같은 답을 준비.

**예상 질문**
- **Q. 슬롯 충족은 LLM이 판단했나요, 룰이었나요?**
- **Q. 사용자가 계속 성의 없이 답하면 무한루프 아닌가요?** → Probe 상한 + 진행 강제.
- **Q. 슬롯 평가의 정확도는 어떻게 검증했나요?** → **여기가 약점**. 골든셋 몇 건 만들어 수동 라벨링했다 정도라도 준비. 없으면 "정량 평가 체계가 없었던 게 이 프로젝트의 가장 큰 아쉬움" 이라고 먼저 인정하는 편이 낫다.

### LLM 우선 + 규칙 기반 폴백
표준 용어 **Graceful Degradation** 또는 **Fallback Chain**.

**폴백 계층을 단계로 설명하면 좋다**
```
1차: 기본 모델 호출
2차: 재시도 (지수 백오프 + 지터, Retry-After 준수)
3차: 대체 모델/대체 리소스로 라우팅   ← 자소서의 '모델 스위처'와 연결
4차: 규칙 기반 템플릿 응답 (미리 작성된 문구 + 슬롯 치환)
5차: 사용자에게 상태 고지 + 진행 저장 후 이어하기
```

| 관련 패턴 | 설명 | 물어볼 만한 것 |
|---|---|---|
| **서킷 브레이커** | 연속 실패 시 회로 차단, 일정 시간 호출 자체를 안 함 | "실패한 API를 계속 때리진 않았나요?" (`pybreaker`, `purgatory`) |
| **타임아웃 + 예산(deadline)** | 요청 전체에 시간 상한 | LLM은 응답이 느려서 필수 |
| **벌크헤드** | 기능별 리소스 격리 | 이미지 생성 장애가 채팅을 막지 않게 |
| **tenacity** | Python 재시도 라이브러리 표준 | 직접 구현했다면 왜인지 |

**예상 질문**
- **Q. 서킷 브레이커는 안 두셨나요?** → 있으면 임계값(연속 실패 N회/시간창), 없으면 "재시도 상한과 큐 길이 제한으로 사실상의 백프레셔를 걸었고, 정식 브레이커는 다음 개선 항목이었다".
- **Q. 규칙 폴백으로 나간 응답은 사용자에게 표시했나요?** → **품질 정직성 이슈**. "폴백임을 UI에 표시했는지" 여부가 신뢰성 설계 감각을 보여준다.
- **Q. 폴백 발동률은?** → 숫자 준비(부록 B).

## 1-4. 검색 고도화 문단 ★배점 높음

> **원문**
> 검색 고도화 측면에서는 Neo4j 기반 GraphRAG를 도입해 관계형 컨텍스트 기반으로 Retrieval 구조를 재설계하고 인덱싱과 질의 경로를 최적화했습니다. 또한 장문 필드를 청크로 분할해 키워드와 시멘틱을 결합한 하이브리드 검색으로 정확도를 높였고, LLM 요약 배치는 캐싱과 병목 구간 분석으로 처리 속도를 약 30% 이상 개선했습니다.

**등장 키워드**: GraphRAG · Neo4j · 관계형 컨텍스트 · 인덱싱/질의 경로 최적화 · 청킹 · 하이브리드 검색 · 캐싱 · 30% 개선

### RAG 기본기 (되물음의 출발점)
```
문서 → 청킹 → 임베딩 → 벡터 저장 → [질의] → 검색(top-k) → 리랭킹 → 프롬프트 조립 → 생성
```
각 단계마다 "왜 그 값이었나"를 물을 수 있다. **top-k 값, 청크 크기, overlap, 임베딩 모델명** 이 4개는 숫자로 외워둘 것.

### GraphRAG
"그래프 기반 RAG"는 사실 **두 가지 다른 것**을 가리킨다. 이걸 구분하면 바로 앞서간다.

| 구분 | 설명 | 대표 |
|---|---|---|
| **(A) 지식그래프 기반 검색** | 도메인 엔티티·관계를 그래프로 모델링하고, 자연어 질의를 그래프 탐색(Cypher)으로 변환해 근거를 회수 | 내가 한 것 (Neo4j + 온톨로지) |
| **(B) Microsoft GraphRAG** | LLM이 문서에서 엔티티·관계를 자동 추출 → 커뮤니티 탐지(Leiden) → 커뮤니티 요약 → Global/Local Search | 오픈소스 패키지. "그거 쓰신 건가요?" 질문 주의 |

**(A)를 했다면 이렇게 말한다**: "MS GraphRAG처럼 문서에서 그래프를 자동 생성한 방식이 아니라, 도메인 엔티티와 관계를 직접 온톨로지로 설계하고 그 위에서 탐색한 구조입니다."

**GraphRAG가 벡터 RAG보다 나은 지점 (이유를 대야 한다)**
- **다중 홉 질의** — "A와 유사한 조건에서 사고가 났던 사례" 처럼 관계를 2~3단계 타야 답이 나오는 질문
- **집계형 질의** — "이 유형 전체에서 공통된 위험요인" (벡터 검색은 top-k만 봐서 전체를 못 본다)
- **설명가능성** — 근거를 "문서 조각"이 아니라 "경로(path)"로 제시 → 4부 금융 설명가능성과 직결
- **미시험 조합 추론** — 이력서의 CT 성적서 POC에서 실제로 한 것

**단점도 말할 것**: 그래프 구축·유지 비용, 스키마 변경 시 재작업, 질의 지연시간 증가, Text2Cypher의 정확도 문제.

#### Neo4j 주변 용어

| 용어 | 설명 |
|---|---|
| **Cypher** | Neo4j 질의어. `MATCH (a)-[:REL]->(b) RETURN b` |
| **LPG vs RDF** | LPG(Labeled Property Graph)=노드/관계에 속성 부여, 실무 친화. RDF=트리플(주어-술어-목적어), 표준·추론(OWL) 강점. **이력서에 "비교 검토 후 Neo4j 선택"이라고 썼으므로 이유를 반드시 준비** |
| **온톨로지** | 도메인 개념·관계·제약의 형식적 정의. RDF/OWL 세계의 용어 |
| **Text2Cypher** | 자연어 → Cypher 변환. LLM이 함. 스키마를 프롬프트에 주입하는 게 관건 |
| **Neo4j 벡터 인덱스** | 5.11+ 부터 벡터 인덱스 내장 → 그래프+벡터 하이브리드를 한 DB에서 |
| **APOC / GDS** | 확장 프로시저 / 그래프 데이터사이언스 라이브러리(중심성, 커뮤니티 탐지, 유사도) |

**LPG vs RDF 답변 뼈대**: "RDF는 표준화와 추론(OWL reasoner)에 강하지만, 우리 도메인은 관계에 속성(시험 조건, 측정값)을 붙여야 했고 개발자가 바로 읽을 수 있는 모델이 필요했습니다. 트리플로 표현하면 reification이 필요해 복잡도가 커져 LPG를 택했습니다."

#### 그래프/벡터 저장소 대체 기술

| 제품 | 성격 | 비교 포인트 |
|---|---|---|
| **Amazon Neptune** | 관리형, LPG(Gremlin)+RDF(SPARQL) 둘 다 | 클라우드 관리형 원하면 |
| **TigerGraph** | 대규모 분석 특화 | 초대형 그래프 |
| **Memgraph / Kùzu** | 인메모리 / 임베디드. Cypher 호환 | 가볍게 쓸 때 |
| **ArangoDB** | 멀티모델(문서+그래프) | 문서 저장까지 한 번에 |
| **GraphDB / Stardog / Virtuoso** | RDF 트리플스토어 | 온톨로지·추론 필요하면 |
| **LlamaIndex PropertyGraphIndex** | 코드로 그래프RAG 구성 | 프레임워크 대안 |

| 벡터DB | 특징 |
|---|---|
| **FAISS** | 라이브러리. 이력서에서 실제 사용. 서버·필터·영속성 없음 |
| **Chroma** | 로컬/프로토타입 친화. 이력서에서 사용 |
| **Qdrant** | Rust, 필터링 성능 좋음, 하이브리드 지원 |
| **Weaviate / Milvus** | 하이브리드 내장 / 초대규모 |
| **pgvector** | Postgres 확장. 운영 단순화 |
| **Azure AI Search** | **Azure 쓴다면 1순위 되물음**. BM25+벡터 하이브리드 + RRF + 시맨틱 랭커 내장 |
| **Elasticsearch / OpenSearch** | 키워드 강점 + kNN. ELSER(학습된 희소검색) |

> **주의**: 자소서엔 Elasticsearch, 이력서엔 FAISS/Chroma가 나온다. "왜 프로젝트마다 다른가"를 물으면 → 도입 시점·요구사항 차이(운영형 vs POC)로 답한다.

### 하이브리드 검색
**Sparse(BM25, 키워드 정확 일치) + Dense(임베딩, 의미 유사도)** 를 함께 쓰고 결과를 융합.

- **왜 필요한가**: 벡터만 쓰면 고유명사·모델명·코드값(예: "KC-2024-117")을 놓친다. BM25만 쓰면 동의어·의역을 놓친다.
- **융합 방식**
  - **RRF (Reciprocal Rank Fusion)**: `score = Σ 1/(k + rank)`, 보통 k=60. **점수 스케일이 달라도 되는 게 장점** → 실무 기본값
  - **가중합(Convex/Linear)**: `α·정규화(dense) + (1-α)·정규화(sparse)`. 스케일 정규화 필요, 튜닝 가능
  - **Cross-encoder 리랭킹**: 후보 50~100개를 뽑아 쿼리-문서 쌍을 함께 인코딩해 재정렬. 정확도 최고, 비용 최대

> **"융합은 RRF인가요 가중합인가요?"** 는 실제로 잘 나오는 질문. 무엇을 썼는지 + 왜인지를 준비.

| 리랭커 | 비고 |
|---|---|
| **Cohere Rerank** | API형, 성능 좋음 |
| **BGE-reranker / Jina Reranker** | 오픈모델, 온프렘 가능 (금융권 폐쇄망과 연결) |
| **Elasticsearch Learning to Rank / ELSER** | ES 생태계 내장 |

### 청킹 (Chunking)
"장문 필드를 청크로 분할" → 표준 용어로 정리.

| 전략 | 설명 | 언제 |
|---|---|---|
| **고정 크기 + overlap** | N토큰 단위, 10~20% 겹침 | 기본값 |
| **Recursive character split** | 문단→문장→단어 순으로 재귀 분할 | LangChain 기본, 무난 |
| **문서 구조 기반** | 헤딩·섹션·표 단위 | 성적서/규정 문서처럼 구조가 뚜렷하면 최적 |
| **Semantic chunking** | 문장 임베딩 유사도가 끊기는 지점에서 분할 | 비용↑ |
| **Parent-Child (small-to-big)** | 작은 청크로 검색, 부모 문단을 LLM에 전달 | 정확도/컨텍스트 둘 다 잡음. **추천 답변 소재** |
| **Contextual Retrieval** | 각 청크 앞에 문서 요약 문맥을 LLM으로 붙여 저장 (Anthropic 제안) | 정확도 큰 향상, 인덱싱 비용↑ |
| **Late chunking** | 긴 문맥으로 임베딩 후 잘라내기 | 최신 기법 |

**예상 질문**: "청크 크기와 overlap은 얼마였고 어떻게 정했나요?" → 실험으로 정했다면 그 지표를, 감으로 정했다면 "기본값에서 시작해 실패 사례 보고 조정했다"고 정직하게.

### 캐싱 + 30% 개선 ★숫자 방어 필수
"LLM 요약 배치는 캐싱과 병목 구간 분석으로 처리 속도를 약 30% 이상 개선"

**분해해서 말할 수 있어야 한다**
- **무엇을 캐싱했나**: (a) 입력 해시 → 요약 결과 (b) 임베딩 결과 (c) 프롬프트 캐싱(공통 프리픽스)
- **캐시 저장소**: 인메모리(dict/LRU) vs Redis vs DB 컬럼. 재기동 시 유실 여부
- **캐시 키 설계**: 원문 해시 + 모델명 + 프롬프트 버전 (**이 3개를 다 넣어야 모델 교체 시 오염이 없다** — 말하면 좋은 디테일)
- **무효화 전략**: TTL / 원문 변경 시 갱신
- **병목 구간 분석 방법**: 어떻게 쟀나? (구간별 타이머 로깅 / cProfile / py-spy / APM)
- **30%의 기준**: 무엇 대비 무엇인가. 전체 배치 소요시간? 건당 평균? 측정 횟수는?

| 캐싱 유형 | 설명 |
|---|---|
| **Exact-match 캐시** | 입력 해시 일치 시 재사용. 안전 |
| **Semantic 캐시** | 유사 질의도 히트(GPTCache 등). **오답 재사용 위험** — 금융권엔 부적절 |
| **프롬프트 캐싱** | 공통 시스템 프롬프트 부분을 서버가 캐시 → 비용·지연 감소 |
| **임베딩 캐시** | 동일 텍스트 재임베딩 방지. 비용 절감 효과 큼 |

**예상 질문**
- **Q. 30%는 어떻게 측정했나요? 캐시 워밍 상태에서 잰 건 아닌가요?** → **가장 아픈 질문**. 측정 조건(콜드/웜, 샘플 수)을 미리 정리.
- **Q. 캐시 히트율은?** → 모르면 "히트율을 지표로 두지 않은 게 아쉬웠다"고 인정.
- **Q. 요약 품질은 캐시로 바뀌지 않았나요?** → 프롬프트 버전을 키에 포함했는지가 답.

### RAG 평가 ★자소서 최대 구멍
자소서 전체에 **평가(Evaluation) 이야기가 한 줄도 없다.** "정확도를 높였다"고만 썼으므로 "어떻게 측정했나요?"가 반드시 온다.

최소한 이 용어들은 알고 갈 것:
- **검색 지표**: Recall@k, Precision@k, MRR, nDCG, Hit Rate
- **생성 지표**: Faithfulness(근거 충실성), Answer Relevancy, Context Precision/Recall — **RAGAS** 프레임워크의 4대 지표
- **LLM-as-a-Judge**: LLM으로 채점. 편향(위치·장황함 선호) 주의
- **골든 데이터셋**: 질문-정답-근거문서 쌍을 수십~수백 건 수동 구축
- **도구**: RAGAS, DeepEval, TruLens, Phoenix(Arize), Langfuse, LangSmith, Azure AI Foundry Evaluation

> **정직 전략**: "정량 평가 체계를 갖추지 못한 채 도메인 전문가의 정성 검토에 의존했습니다. 그게 이 프로젝트에서 제가 꼽는 가장 큰 한계이고, 다음 프로젝트에선 골든셋 기반 회귀 평가를 CI에 넣는 것부터 시작할 겁니다." — 이렇게 답하면 오히려 가점이 된다.

**여기서만 짚을 지뢰 3개**

|---|---|---|
| **"20명 동시 접속"** | 프로덕션 규모로는 작다. "그 정도로 왜 문제가?" 라고 되물음 | "동시 사용자 수 자체보다 **이미지 생성 쿼터(TPM/분당 요청)** 가 병목이었습니다. 사용자 20명이 각자 산출물 여러 장을 동시에 요청하면 순간 요청량이 쿼터를 훨씬 넘습니다." — **부하의 단위를 사용자 수가 아니라 API 호출량으로 재정의**하는 게 핵심 |
| **"100% 완주"** | 어떤 표본에서? 100%는 공학적으로 위험한 단어 | "**설계 목표가 100% 완주**였고, 부하 테스트 N회 및 운영 기간 중 미완주 케이스는 없었습니다" 로 범위를 한정 |
| **"현업 업무 시간을 대폭 단축"** | 정량 요구 확실 | 기존 소요시간 → 개선 후 소요시간, 근거(현업 인터뷰/로그) 준비 (부록 B) |

**예상 질문**

- **Q. 큐가 인메모리였나요? 서버 재기동하면 대기 요청은?** → 유실 여부와 재개 설계.

## 2-2. 리소스 분리 · 모델 스위처 문단

> **원문**
> Azure OpenAI를 Chat용과 이미지 생성용 리소스로 물리적 분리하여 트래픽 성격과 쿼터를 독립적으로 관리했습니다. 또한, 어드민에서 런타임에 LLM과 이미지 모델을 전환할 수 있는 모델 스위처를 구현해 코드 수정 없이 즉각적인 교체와 A/B 비교가 가능하도록 했습니다. GPU 및 API 자원이 소모되는 워크로드에 대해서는 배치 처리 시점을 분산하고 동시 호출 수를 자원 한계에 맞춰 제어하여 추론 병목과 과금 리스크를 동시에 방어했습니다.

**등장 키워드**: 리소스 물리적 분리 · 쿼터 독립 관리 · 모델 스위처 · A/B 비교 · 배치 시점 분산 · 동시 호출 제어

### 리소스 분리 = 벌크헤드(Bulkhead) 패턴
"이미지 생성이 쿼터를 다 써도 채팅은 살아있게" — 이게 **벌크헤드 패턴**이다. 이 단어로 말하면 설계 의도가 즉시 전달된다.

부수 효과까지 말하면 좋다: ①쿼터 독립 ②비용 귀속 분리(코스트 태깅) ③키 분리로 권한 최소화(4부 연결) ④장애 영향 격리.

### 모델 스위처 (런타임 모델 전환)
어드민에서 배포명(deployment)을 바꿔 코드 수정·재배포 없이 모델 교체.

| 대체 기술 | 설명 | 되물음 |
|---|---|---|
| **LiteLLM Proxy** | 100+ 모델 통합 프록시. 라우팅·폴백·쿼터·비용추적 내장 | "이런 게 이미 있는데 왜 직접?" |
| **Azure API Management** | 게이트웨이. 다중 Azure OpenAI 백엔드 로드밸런싱, 토큰 기반 쿼터 정책 | Azure 정석 패턴 |
| **OpenRouter / Portkey / Helicone** | 라우팅·관측 SaaS | |
| **Azure AI Foundry 모델 라우터** | 요청별 최적 모델 자동 선택 | 최근 기능 |

> **답변 뼈대**: "요구가 '어드민에서 즉시 전환 + 사용자별 A/B'로 좁았고, 프록시를 하나 더 운영하는 비용보다 서비스 계층에 팩토리 하나 두는 게 단순했습니다. 다만 모델이 늘고 팀이 여럿이 되면 LiteLLM이나 APIM 게이트웨이로 올리는 게 맞습니다."

### A/B 비교 — 여기 파고들면 아플 수 있다
"A/B 비교가 가능하도록 했다"는 **기능 제공**이고, 실제로 **A/B 테스트를 수행**한 것과는 다르다.

- 트래픽 분배는 어떻게? (사용자 해시 고정? 랜덤? 어드민 수동 전환?)
- 비교 지표는? (응답 길이? 사람 선호? 완주율? 비용?)
- 통계적 유의성은 봤나?

> **정직 전략**: "본격적인 온라인 A/B 테스트라기보다, 동일 입력에 대해 모델을 전환해 **정성 비교(side-by-side)** 를 빠르게 하기 위한 장치였습니다."

### 배치 시점 분산 · 동시 호출 제어
- **배치 시점 분산** = 스케줄 스태거링(staggering) / 지터 삽입. 여러 배치가 정각에 몰리는 **thundering herd** 방지.
- **동시 호출 제어** = `asyncio.Semaphore(N)` 또는 워커 풀 크기 제한. **N값과 그 근거를 반드시 기억할 것.**
- **과금 리스크 방어** = 비용 가드레일. 관련 개념: 토큰 예산(budget), Azure Cost Management 예산 알림, 요청당 max_tokens 상한, 사용자별 쿼터.

**예상 질문**
- **Q. 동시 호출 수는 몇으로 정했고 근거는?** → 3부 부하테스트 결과와 연결해서 답한다.
- **Q. 쿼터 증설 요청은 안 해봤나요? PTU는?** → "요청했으나 리전/구독 한도가 있었다" 또는 "비용 대비 판단" 등.
- **Q. 모델을 바꾸면 프롬프트도 다시 튜닝해야 하지 않나요?** → **좋은 질문. 준비 필수.** 모델별 프롬프트 버전 관리 여부, 스키마 준수율 차이 경험 등.

## 2-3. 백엔드 · 인증 문단

> **원문**
> 백엔드는 FastAPI(async) 기반의 비동기 API 서버를 개발하여 LLM 호출을 Async I/O로 처리함으로써 동시 요청 대기 시간을 최소화했습니다. JWT 인증과 전화번호 Allowlist 기반의 접근 통제를 적용해 보안성을 높였고, LLM·이미지 생성·검색·요약 등 외부 연동 로직을 재사용 가능한 서비스 계층으로 모듈화하여 확장성과 유지보수성을 확보했습니다.

**등장 키워드**: Async I/O · JWT · Allowlist · 서비스 계층 모듈화

### Async I/O
**한 문장 정의**: "LLM 호출은 CPU를 쓰는 게 아니라 응답을 기다리는 시간이 대부분이므로, 기다리는 동안 이벤트 루프가 다른 요청을 처리하게 만드는 것."

물어볼 만한 것:
- **동시성 vs 병렬성** 차이 (asyncio는 동시성, GIL 때문에 CPU 병렬은 아님)
- **`asyncio.gather` vs `TaskGroup`** — 부분 실패 처리 차이
- **스트리밍** — SSE로 토큰 단위 전송했는지. 체감 지연(TTFT, Time To First Token)을 줄이는 핵심
- **워커 구성** — uvicorn 워커 수, gunicorn+uvicorn worker 조합

### JWT
| 항목 | 알아야 할 것 |
|---|---|
| 구조 | Header.Payload.Signature (Base64URL). **페이로드는 암호화가 아니라 인코딩** — 민감정보 넣으면 안 됨 |
| 서명 | HS256(대칭) vs RS256(비대칭). 검증 주체가 여럿이면 RS256 |
| 만료·갱신 | access token 단기 + refresh token. **회전(rotation)** 과 재사용 탐지 |
| 취약점 | 즉시 로그아웃(무효화)이 어렵다 → 블랙리스트/짧은 만료로 보완 |
| 저장 위치 | localStorage(XSS 취약) vs httpOnly 쿠키(CSRF 대비 필요) — **"어디에 저장했나요?"가 실제로 나온다** |

| 대체 | 비교 |
|---|---|
| **세션 + Redis** | 즉시 무효화 가능, 서버 상태 필요 |
| **OAuth2 / OIDC** | 표준 위임 인증 |
| **Microsoft Entra ID (구 Azure AD)** | **Azure를 썼는데 왜 자체 JWT?** 되물음 1순위. SSO·조건부 액세스·MFA 무료로 얻음 |

> **답변 뼈대**: "사내 단기 서비스라 Entra ID 연동 승인 절차보다 자체 발급이 빨랐습니다. 다만 사용자 수가 늘거나 감사 요건이 생기면 Entra ID로 옮기는 게 맞고, 금융권이라면 처음부터 그렇게 갔을 겁니다."

### 전화번호 Allowlist
사전 등록된 번호만 접근 허용하는 **화이트리스트 방식 접근통제**.

- **장점**: 가장 단순하고 확실한 통제
- **약점(물어볼 것)**: 전화번호는 **개인정보이자 식별자**다. 저장 시 암호화/해시했는지, 인증(OTP)은 있었는지 — **전화번호를 알기만 하면 사칭 가능한 구조 아니었나?** 가 날카로운 질문
- **답변**: 실제 구조를 정직히 말하되 "사내 파일럿 범위에서 위험 수용, 대외 서비스면 OTP 또는 SSO가 필수" 로 마감
- **관련 용어**: RBAC(역할 기반), ABAC(속성 기반), 최소권한 원칙(PoLP)

### 서비스 계층 모듈화
**용어로 승격시켜 말하기**: 레이어드 아키텍처(Controller-Service-Repository), 의존성 역전(인터페이스로 LLM 프로바이더 추상화), 어댑터/포트 패턴(헥사고날), 전략(Strategy) 패턴 = 모델 스위처의 실체.

**예상 질문**: "LLM 프로바이더를 인터페이스로 추상화했다면, OpenAI 말고 다른 벤더로 갈아끼우는 데 얼마나 걸리나요?" → 실제 소요 추정치로 답하면 설계 진정성이 증명된다.

## 2-4. 부하 테스트 · 런타임 노브 문단

> **원문**
> 다중 사용자 동시 접속 환경의 성능 병목을 정량 진단하기 위해 가상 사용자 동시 요청 기반의 부하 테스트 도구를 직접 구현했습니다. 이를 통해 큐 적체와 429 에러를 관찰하고, 이미지 생성 동시성 파라미터, DB 커넥션 풀, 우선순위 큐 정렬 기준을 세밀하게 튜닝했습니다. 아울러 .env 기반의 런타임 노브(선생성 토글, 동시성 제어 등)를 도입해 재배포 없이 유연한 실시간 부하 대응 체계를 마련했습니다.

**등장 키워드**: 합성 부하 테스트 · 커넥션 풀 튜닝 · .env 런타임 노브

### 부하 테스트 — "왜 직접 만들었나"
| 도구 | 특징 | 되물음 |
|---|---|---|
| **Locust** | Python으로 시나리오 작성. **가장 직접적인 대체제** | "Locust 쓰면 됐을 텐데?" |
| **k6** | JS 시나리오, Go 엔진. 지표·임계값(threshold) 관리 우수 | 현재 업계 표준에 가까움 |
| **JMeter** | GUI, 엔터프라이즈에서 여전히 표준 | 금융권에서 익숙한 이름 |
| **Gatling / Vegeta / artillery** | Scala DSL / 단순 HTTP / Node | |
| **Azure Load Testing** | JMeter/k6 관리형 | Azure 정석 |

> **답변 뼈대**: "단순 HTTP 부하가 아니라 **진단 대화 시나리오 전체를 상태를 유지하며 순서대로 밟아야** 했고, 서버 내부 큐 길이·429 카운터를 같은 화면에서 봐야 했습니다. 그래서 도메인 시나리오에 특화된 스크립트를 직접 만들었습니다. 순수 부하만 봤다면 Locust나 k6가 정답입니다."
> — **핵심은 "도메인 상태 시나리오"라는 정당화**. 이게 없으면 "바퀴 재발명"으로 읽힌다.

**측정했어야 할 지표(용어 정리)**: RPS/TPS, **p50·p95·p99 지연**, 에러율, 동시성 수준별 처리량 곡선, 큐 대기시간, 포화점(knee point).
> 평균만 봤다면 "평균은 꼬리를 못 본다"는 걸 알고 있다고 말하는 편이 낫다.

### DB 커넥션 풀
- **핵심 공식 감각**: 워커 수 × 요청당 커넥션 ≤ pool_size + max_overflow ≤ **PostgreSQL `max_connections`**
- Postgres는 커넥션 하나가 프로세스라 **많을수록 좋은 게 아니다**. 과도한 풀은 오히려 성능 저하 → **PgBouncer** 같은 커넥션 풀러가 표준 해법
- 관련 파라미터: `pool_size`, `max_overflow`, `pool_timeout`, `pool_recycle`, `pool_pre_ping`

**예상 질문**: "커넥션 풀을 얼마로 올렸나요? 그게 왜 병목이었나요?" → 숫자 + 증상(요청 대기 timeout, `QueuePool limit reached` 에러) 준비.

### .env 런타임 노브 ★약점 주의
> **함정**: `.env`는 보통 **프로세스 시작 시 1회 로드**된다. 그러면 "재배포 없이"는 맞아도 **"재기동 없이"는 아니다.** 면접관이 "재기동 없이 반영되나요?"라고 물으면 정확히 답해야 한다.

가능한 답 3가지 — 실제 구현에 맞게 하나를 고를 것:
1. "컨테이너 재기동은 필요했고, 무중단은 아니었습니다. 다만 코드 빌드·배포 파이프라인은 안 타서 반영이 분 단위였습니다."
2. "값을 매 요청마다 다시 읽도록(`os.getenv` 호출 시점 지연) 구현해 파일 변경만으로 반영됐습니다."
3. "일부는 어드민에서 DB로 관리해 즉시 반영됐고, 나머지는 .env였습니다."

| 정석 대체 | 설명 |
|---|---|
| **Azure App Configuration** | 중앙 설정 + 동적 갱신 + 기능 플래그. **Azure 정답** |
| **Azure Key Vault** | 비밀값 전용(키·커넥션 스트링) |
| **LaunchDarkly / Unleash / Flagsmith** | 기능 플래그 SaaS/오픈소스. 점진적 롤아웃·타깃팅 |
| **Redis/DB 기반 자체 설정 테이블** | 가장 흔한 실무 절충안 |

**예상 질문**
- **Q. API 키도 .env에 있었나요? 소스에 커밋된 적은?** → Key Vault / Managed Identity를 알고 있다고 말할 것.
- **Q. 노브를 잘못 돌리면 장애 아닌가요? 값 범위 검증은?** → 가드레일(min/max clamp), 변경 로그 남겼는지.

## 2-5. 배포 · 이중화 · 컴플라이언스 문단

> **원문**
> 로컬 개발 환경과 nginx 정적 빌드가 적용된 운영 배포 환경을 2벌의 Docker-compose로 표준화하여 배포 안정성을 높였습니다. 외부 AI 서비스 장애 시 규칙 기반 폴백 메커니즘으로 서비스를 중단 없이 이중화했으며, 개인정보 익명화 배치 작업을 자동 스케줄러로 운영해 컴플라이언스를 준수했습니다. 이를 통해 클라우드 환경 내 AI 서비스를 무중단에 가깝게 안정적으로 운영한 실전 역량을 갖추었습니다.

**등장 키워드**: docker-compose 2벌 · nginx 정적 빌드 · 규칙 기반 이중화 · 개인정보 익명화 배치 · 자동 스케줄러

### docker-compose 2벌 + nginx
- **nginx 정적 빌드**: React를 `npm build`로 정적 파일화 → nginx가 서빙 + `/api` 리버스 프록시. SPA라면 `try_files ... /index.html` 폴백 설정이 필수(라우팅 새로고침 404 방지) — 실제 겪었으면 좋은 디테일.
- **왜 2벌인가**: 개발은 핫리로드·볼륨 마운트, 운영은 빌드 이미지·nginx. 표준 대안은 `compose.override.yml` 또는 profiles로 한 벌 유지.

**되물음 대비**
- **Q. 무중단 배포는 어떻게?** → compose 단독으론 짧은 다운타임 발생. 정직하게 말하고 "블루-그린 / 롤링 업데이트가 필요하면 Container Apps나 AKS" 로 확장 경로 제시.
- **Q. CI/CD는?** → GitHub Actions / Azure DevOps Pipelines 사용 여부. 없었다면 수동 배포였다고 말하고 아쉬운 점으로.
- **Q. 이미지 태깅·롤백은?** → `latest` 쓰면 롤백 불가. 커밋 SHA 태깅 여부.

> **"무중단에 가깝게"** 라는 표현은 정확히는 **애플리케이션 레벨 가용성(폴백으로 사용자 흐름이 안 끊김)** 이지, **인프라 레벨 HA(다중 인스턴스·무중단 배포)** 가 아니다. 이 구분을 스스로 먼저 말하면 신뢰가 크게 오른다.

### 개인정보 익명화 배치 ★4부와 연결되는 핵심 카드
**용어를 정확히 구분해야 한다 — 개인정보보호법 기준**

| 용어 | 정의 | 재식별 | 활용 |
|---|---|---|---|
| **가명처리(가명정보)** | 추가정보 없이는 특정 개인을 못 알아보게 | 추가정보 결합 시 가능 | 통계·연구·기록보존 목적은 동의 없이 가능 |
| **익명처리(익명정보)** | 시간·비용·기술을 합리적으로 고려할 때 복원 불가능 | 불가 | **개인정보보호법 적용 대상에서 제외** |
| **마스킹** | 표시 일부 가림(홍*동) | 원본이 남아있으면 여전히 개인정보 | 화면 표시 통제 수단 |
| **암호화/토큰화** | 복호화 키·매핑 테이블 존재 | 가능 | 저장 보호 수단이지 비식별화가 아님 |

> **면접 포인트**: "익명화 배치"라고 썼는데 실제로는 **가명처리 또는 마스킹**인 경우가 많다. 실제 구현이 무엇이었는지 정직하게 구분해서 말할 것. 이 구분을 아는 지원자는 드물다.

**관련 개념**: k-익명성, l-다양성, t-근접성, 차분 프라이버시(Differential Privacy), 보존기간·파기 정책(retention), **Microsoft Presidio**(PII 탐지·비식별 오픈소스), Azure AI Language PII Detection.

### 자동 스케줄러
| 방식 | 특징 |
|---|---|
| **APScheduler** | Python 인프로세스 스케줄러. 가장 흔함. **다중 인스턴스면 중복 실행 위험** |
| **cron / systemd timer** | OS 레벨, 단순 확실 |
| **Celery Beat** | 분산 워커와 결합 |
| **Airflow / Dagster / Prefect** | 의존성 있는 데이터 파이프라인 |
| **Azure Functions Timer / Logic Apps / Container Apps Jobs** | 서버리스 스케줄. Azure 정석 |

**예상 질문**: "서버가 2대로 늘면 배치가 두 번 도는 거 아닌가요?" → 분산 락(Redis/DB advisory lock) 또는 리더 선출. **모르면 여기서 막힌다.**

# 3부. [데이터 기반의 정량적 진단과 아키텍처 개선으로 동시 접속 부하]

> 1부 후반과 같은 사건. **여기서는 이론 용어로 무장한다.**

## 3-1. 문제 정의 문단

> **원문**
> 대화형 AI 진단 서비스를 프로덕션에 적용하는 과정에서, 20명이 동시에 접속해 산출물(이미지·캔버스)을 생성할 때 시스템이 급격히 불안정해지는 문제가 발생했습니다. 이미지 생성 요청이 몰리면서 Azure OpenAI에서 429(Rate Limit 초과) 오류가 반복되었고, 대기 요청이 큐에 적체되며 응답 지연과 실패가 속출했습니다. 단순히 동시성을 낮추면 전체 처리량이 떨어지고, 높이면 429가 폭증하는 딜레마 상황이었습니다.

**등장 키워드**: 429 · Rate Limit · 큐 적체 · 처리량/지연 트레이드오프

### 429와 레이트 리밋 이론
- **429 Too Many Requests** — 서버가 클라이언트 요청률을 제한. 응답 헤더 **`Retry-After`** 에 재시도까지의 초(또는 시각)를 담는다. Azure OpenAI는 TPM/RPM 초과 시 발생.
- **주의**: 429는 재시도해도 되는 오류(retryable), 400/401은 재시도하면 안 되는 오류. **재시도 대상을 상태코드로 구분했는지**가 실무 감각.

**레이트 리밋 알고리즘 4종 — 이름만 알아도 대화가 달라진다**

| 알고리즘 | 동작 | 버스트 허용 |
|---|---|---|
| **토큰 버킷** | 일정 속도로 토큰 충전, 요청마다 소비 | O (버킷 크기만큼) |
| **리키 버킷** | 고정 속도로 새어나감 = 출력이 일정 | X (평탄화) |
| **고정 윈도우 카운터** | 1분 단위 카운트 | 경계에서 2배 버스트 발생 |
| **슬라이딩 윈도우 로그/카운터** | 이동 구간 기준 | 정확, 비용↑ |

> "버스트 평탄화"는 정확히 **리키 버킷의 효과**다. 이 매핑을 말하면 좋다.

### 큐 적체 = Little's Law
**L = λ × W** (대기 중 항목 수 = 도착률 × 평균 대기시간)
- 도착률(λ)이 처리율(μ)보다 크면 큐는 **무한히** 자란다. 동시성 조정으로 μ를 못 올리면 결국 **입구를 막아야(admission control)** 한다.
- **백프레셔(Backpressure)**: 큐가 임계치를 넘으면 새 요청을 거절하거나 지연시켜 상류에 압력을 전달. **"큐를 무한정 늘리는 건 해결이 아니라 지연 폭탄"** 이라는 인식이 핵심.

### 처리량 vs 지연 딜레마
- **포화점(knee point)**: 동시성을 올리면 처리량이 오르다가 어느 지점부터 지연만 급증하고 처리량은 정체/하락.
- **USE / RED 메서드**: 리소스는 Utilization·Saturation·Errors, 요청은 Rate·Errors·Duration으로 본다. 지표 설계 용어로 좋다.
- **Universal Scalability Law**: 경합(contention)과 일관성(coherency) 비용 때문에 무한 확장은 없다는 모델. 이름만 알아도 무게가 실린다.

## 3-2. 정량 진단 문단

> **원문**
> 감으로 파라미터를 조정하는 대신, 원인을 정량적으로 규명하기 위해 두 가지 접근을 취했습니다. 첫째, 어드민 화면에 큐 적체량과 429 누적 카운터를 실시간으로 모니터링하는 기능을 구현했습니다. 둘째, 가상의 N명이 동시 요청을 발사하는 합성 부하 테스트 도구를 직접 개발해 동시성 수준별 에러율과 응답 지연을 반복 측정했습니다. 분석 결과, 병목의 핵심은 '이미지 생성 동시 호출 수'와 '버스트 트래픽의 처리 순서'에 있음을 확인했습니다.

**등장 키워드**: 실시간 모니터링 · 누적 카운터 · 합성 부하 테스트

### 관측(Observability) 표준 용어 — 자소서에서 비어있는 부분
자소서는 "어드민 화면에 카운터"라고 썼다. 이건 사실상 **자체 구현 메트릭**이다. 표준 스택을 알고 있다고 말해야 한다.

| 축 | 설명 | 도구 |
|---|---|---|
| **Metrics** | 수치 시계열(카운터/게이지/히스토그램) | Prometheus + Grafana, Azure Monitor |
| **Logs** | 이벤트 기록. 구조화 로깅(JSON) + correlation ID | Loki, Azure Log Analytics |
| **Traces** | 요청 단위 구간 추적 | **OpenTelemetry**, Jaeger, Application Insights |
| **LLM 특화** | 프롬프트·토큰·비용·평가까지 추적 | **Langfuse**, LangSmith, Phoenix(Arize), Helicone |

> **한 문장 방어**: "당시엔 필요한 지표만 어드민에 직접 노출했지만, 지금 다시 한다면 OpenTelemetry로 트레이스를 심고 LLM 호출 구간은 Langfuse 같은 도구로 프롬프트·토큰·지연을 함께 보는 게 맞다고 봅니다."

**꼭 준비할 지표 4개**: 큐 길이(현재/최대), 429 누적 및 분당 발생률, 생성 지연 p95, 완주율(퍼널).

## 3-3. 해결책 문단

> **원문**
> 이를 해결하기 위해 세 가지 개선책을 동시에 적용했습니다. 첫째, 실측 데이터를 근거로 이미지 생성 동시성을 최적의 수치로 조정하여 429 에러의 급증을 방어했습니다. 둘째, 사용자의 클릭 요청을 최우선으로 두고 나머지는 라운드로빈 방식으로 처리하는 우선순위 큐를 도입해 버스트를 평탄화하고 공정성을 확보했습니다. 셋째, Retry-After 기반 재시도 로직과 대기 시간에 산출물을 미리 만드는 선생성(Pre-commit) 토글을 추가해 체감 지연을 대폭 줄였습니다.

**등장 키워드**: 동시성 최적값 · 우선순위 큐 · 라운드로빈 · 공정성 · Retry-After 재시도 · 선생성(Pre-commit)

### 우선순위 큐 + 라운드로빈 = Fair Queuing
정확한 표준 용어는 **Fair Queuing / Weighted Fair Queuing / Deficit Round Robin**. 네트워크 스케줄링에서 온 개념이다.

**설계 의도를 이렇게 설명한다**
- 순수 FIFO: 한 사용자가 10건을 던지면 뒤의 9명이 전부 그 뒤에 선다 → **head-of-line blocking**
- 순수 우선순위: 낮은 우선순위가 영원히 대기 → **기아(starvation)**
- **사용자별 큐를 두고 라운드로빈으로 한 건씩 꺼내면** → 요청량이 많은 사용자가 다른 사용자를 굶기지 못한다(공정성) + 버스트가 자연히 평탄화

**즉시성(클릭) vs 배경작업(선생성)의 2계층 우선순위**를 라운드로빈과 결합한 구조라고 정리하면 깔끔하다.

| 대체 구현 | 설명 |
|---|---|
| **Redis + RQ/Arq, Celery** | 외부 큐. 재기동에도 유실 없음, 워커 수평 확장 |
| **Azure Service Bus / Storage Queue** | 관리형 큐. 세션 기능으로 순서 보장 |
| **Kafka** | 파티션 = 사용자별 순서 보장. 대규모 |
| **Temporal** | 장기 실행 워크플로우 + 재시도·타임아웃 내장 |
| **asyncio.PriorityQueue (인메모리)** | 내가 한 것에 가장 가까움. 단일 프로세스 한정 |

**예상 질문**
- **Q. 큐가 프로세스 메모리에 있으면 스케일아웃이 안 되지 않나요?** → **정확한 지적이라고 인정**하고 확장 경로(외부 큐) 제시.
- **Q. 기아 상태는 어떻게 막았나요?** → 라운드로빈 자체가 답. 또는 대기시간에 따른 우선순위 승급(aging).

### Retry-After 기반 재시도
표준 재시도 설계 3요소:
1. **지수 백오프(exponential backoff)** — 1s, 2s, 4s, 8s...
2. **지터(jitter)** — 무작위 편차. 없으면 재시도가 동시에 몰려 **thundering herd** 재발. AWS 권장은 **Full Jitter**
3. **상한** — 최대 재시도 횟수 + 전체 데드라인
4. (+) **서버가 준 `Retry-After`를 우선 존중** ← 자소서가 잘한 부분

**멱등성(Idempotency)**: 재시도하면 같은 작업이 두 번 실행될 수 있다. **멱등키(idempotency key)** 로 중복 생성 방지. "재시도했는데 이미지가 두 장 생기지 않았나요?"라고 물어오면 이 단어가 답이다.

### 선생성 (Pre-commit / Speculative Pre-generation)
사용자가 다음 단계를 선택하기 전에 **예상 산출물을 미리 만들어 두는 것**. 표준 용어로는 **prefetch / speculative execution / warm-up**.

- **효과**: 체감 지연(perceived latency) 감소. 실제 처리시간이 아니라 **대기 체감**을 줄이는 UX 최적화
- **비용**: 사용자가 그 선택을 안 하면 생성분이 버려짐 → **낭비율 = 1 - 적중률**. 그래서 **토글**로 만든 것이 합리적
- **말하면 좋은 문장**: "부하가 높을 땐 토글을 꺼서 쿼터를 실사용 요청에 몰아주고, 여유가 있을 땐 켜서 체감 지연을 줄이는 식으로 **자원을 상황에 따라 재배분**하는 스위치였습니다."

**예상 질문**
- **Q. 선생성 적중률은 얼마였나요? 낭비 토큰 비용은?** → 숫자 준비. 없으면 "적중률을 지표화하지 못한 게 아쉽다".
- **Q. 선생성이 오히려 429를 유발하지 않나요?** → **핵심 질문**. 우선순위 큐에서 선생성을 최하위로 두었다는 게 답.

## 3-4. 결과·교훈 문단

> **원문**
> 결과적으로 다중 접속 부하 환경에서도 실패 없이 모든 단계가 안정적으로 완주되도록 시스템을 개선했습니다. 이 경험을 통해 성능 문제는 추측이 아닌 '측정 가능한 지표를 만들고 데이터로 최적점을 찾는다'는 원칙의 중요성을 체득했습니다. 아울러 외부 AI 서비스 연동 시 재시도, 큐, 폴백을 조합한 완충 설계가 프로덕션 안정성의 핵심임을 깊이 깨달았습니다.

**이 문단은 그대로 좋다.** 다만 아래 한 문장을 덧붙일 준비를 해두면 마무리가 강해진다.

> "덧붙이면, 외부 AI는 **가용성을 통제할 수 없는 의존성**이라는 전제에서 설계해야 한다는 걸 배웠습니다. 우리 코드가 아무리 정확해도 상대가 429를 주면 끝이니까요. 그래서 재시도·큐·폴백은 선택이 아니라 기본 요건이라고 생각합니다."

# 4부. [엄격한 보안과 설명가능성을 갖춘 금융·보험 생성형 AI 아키텍처 설계 방안]

> **이 문항이 지원 부서와 가장 직결된다.** 앞 3개는 "무엇을 했나", 이건 "우리 회사에서 무엇을 할 수 있나"를 본다.
> 앞 문항들은 경험이라 방어가 되지만, **이 문항은 지식이라 모르면 바로 드러난다.** 배점상 여기가 최우선.

## 4-1. 4대 축 제시 문단

> **원문**
> 보험·금융 환경에서 생성형 AI를 운영할 때는 보안·개인정보 보호, 설명가능성, 모델 리스크 관리, 내부통제 및 거버넌스가 가장 중요합니다. 금융 데이터는 고객의 민감한 재무·건강·사고 정보를 포함하고, AI의 판단이 보험금 지급 및 심사 등 핵심 의사결정에 직접적인 영향을 미치므로 일반 서비스보다 훨씬 엄격한 통제가 요구됩니다.

**등장 키워드**: 보안·개인정보 보호 · 설명가능성 · 모델 리스크 관리 · 내부통제/거버넌스

### 반드시 알고 가야 할 국내 규제 (이름만 틀려도 티가 난다)

| 규제/가이드 | 핵심 |
|---|---|
| **개인정보보호법(개보법)** | 수집·이용 최소화, 정보주체 동의, 가명정보 특례, **자동화된 결정에 대한 거부·설명요구권**(2024.3 시행) ← **보험 심사 AI와 직결. 반드시 언급** |
| **신용정보법** | 개인신용정보 처리, **프로파일링 대응권(설명요구·이의제기)**, 가명정보 결합(데이터전문기관) |
| **보험업법 / 보험업감독규정** | 인수심사·지급심사의 근거 기록·보존 |
| **전자금융감독규정** | 망분리, 접근통제, 로그 보존. **2024년 금융위 '금융권 망분리 개선 로드맵'** 으로 생성형 AI 활용 규제샌드박스 허용 흐름 ← 최신 동향으로 언급하면 좋음(면접 전 최신 상태 재확인 권장) |
| **금융분야 AI 가이드라인 (금융위)** | AI 개발·활용 단계별 준수사항, 설명가능성·공정성 |
| **금융권 모델리스크관리 모범규준** | 모델 검증·독립적 검토·주기적 재검증 |

### 국제 프레임워크 (한 줄씩만 알면 충분)
- **EU AI Act** — 위험 기반 4단계 분류. **보험 인수·가격 산정(생명·건강)은 고위험(High-risk)** 으로 분류. 이 한 문장이 강력하다.
- **NIST AI RMF 1.0** — GOVERN / MAP / MEASURE / MANAGE 4기능
- **ISO/IEC 42001** — AI 경영시스템 인증 규격(ISO 27001의 AI판)
- **SR 11-7** — 미 연준 모델리스크관리 지침. 국내 모범규준의 원류
- **OWASP Top 10 for LLM** — 프롬프트 인젝션, 민감정보 유출, 공급망, 과도한 대리권(Excessive Agency) 등

**예상 질문**
- **Q. 보험 도메인에서 생성형 AI를 어디에 적용하시겠습니까?** → 준비 필수. 위험도 낮은 것부터: ①사내 문서 검색·규정 Q&A ②상담 콜 요약·후처리 ③약관 비교·설명문 초안 ④청구서류 OCR·분류 ⑤언더라이팅 보조(**의사결정은 사람이**). **"사람의 최종 결정을 대체하지 않는 영역부터"** 라는 원칙을 말할 것.
- **Q. 자동화된 결정에 대한 설명요구권을 아시나요?** → 위 표.

## 4-2. 보안·개인정보 문단

> **원문**
> 첫째, 보안 및 개인정보 보호를 위해 입력 단계에서 개인정보를 마스킹·비식별화하고 최소 정보만 전달해야 합니다. 저는 과거 서비스 운영 시 개인정보 익명화 배치를 설계하고, 리소스와 키를 분리해 접근을 통제한 경험이 있습니다. 금융 환경에서는 폐쇄망(Private Endpoint) 기반의 사내 LLM 서빙과 로그 암호화가 필수적입니다.

**등장 키워드**: 마스킹/비식별화 · 최소 정보 전달 · 리소스·키 분리 · Private Endpoint · 사내 LLM 서빙 · 로그 암호화

### 데이터 흐름 단계별 통제 (이 순서로 말하면 구조적으로 들린다)
```
[수집] 최소수집 · 목적명시
[전처리] PII 탐지 → 마스킹/가명처리 → 필요한 필드만 프롬프트에 주입
[전송] TLS · Private Endpoint(퍼블릭 인터넷 미경유)
[추론] 사내 서빙 or 계약상 데이터 미학습 보장
[저장] 프롬프트·응답 로그 암호화(저장 시 암호화, 키는 KMS/Key Vault) · 보존기간 · 접근 감사
[파기] 보존기간 경과 자동 파기
```

### PII 탐지·비식별 기술

| 기술 | 설명 |
|---|---|
| **정규식/사전 기반** | 주민번호·계좌·전화 패턴. 빠르지만 재현율 한계 |
| **NER 기반 PII 탐지** | **Microsoft Presidio**, Azure AI Language PII, spaCy 커스텀 NER |
| **결정적 가명화(deterministic pseudonymization)** | 같은 값 → 같은 가명. 분석 가능성 유지 |
| **토큰화 / FPE(형식보존암호)** | 형식 유지하며 치환. 매핑 테이블 별도 보관 |
| **차분 프라이버시** | 통계 노출 방어. 개별 서비스엔 과함 |

### 사내 LLM 서빙 (온프렘) — 금융권에서 가장 강력한 카드

| 스택 | 설명 |
|---|---|
| **vLLM** | PagedAttention 기반 고성능 추론 서버. 사실상 표준 |
| **TGI (HuggingFace)** | 대안 추론 서버 |
| **Ollama / llama.cpp** | 소규모·PoC |
| **NVIDIA NIM / Triton** | 엔터프라이즈 GPU 서빙 |
| **모델 후보** | Llama, Qwen, Mistral, **국내: HyperCLOVA X, Solar, EXAONE** |
| **경량화** | 양자화(GPTQ/AWQ/GGUF), LoRA/QLoRA 파인튜닝, 증류 |

> **말하면 좋은 균형 문장**: "폐쇄망 사내 서빙이 규제 대응엔 가장 안전하지만, 모델 성능·운영 인력·GPU 비용이라는 대가가 있습니다. 그래서 **업무를 민감도로 등급화해서 — 대외 비민감 업무는 관리형 API, 고객 민감정보가 닿는 업무는 사내 서빙 — 이원화하는 하이브리드**가 현실적이라고 봅니다."

### 프롬프트 인젝션 (자소서에 없는 구멍)
검색 문서나 사용자 입력에 "이전 지시를 무시하고 ~하라"가 섞여 들어오는 공격. **RAG를 쓰면 문서가 곧 공격 표면**이 된다.

방어책: 입력/출력 가드레일(Azure AI Content Safety **Prompt Shields**, Llama Guard, NeMo Guardrails), 시스템 프롬프트와 데이터의 명확한 구분·구조화, 도구 호출 권한 최소화, 출력 검증, 사람 승인 게이트.

**예상 질문**
- **Q. RAG 문서에 악의적 지시가 들어있으면 어떻게 막나요?** → 위 방어책.
- **Q. LLM에 보낸 프롬프트와 응답 로그 자체가 개인정보 아닌가요?** → **날카로운 질문.** 로그도 개인정보 처리이며 암호화·접근통제·보존기간 대상이라고 답해야 한다.
- **Q. 마스킹하면 답변 품질이 떨어지지 않나요?** → 트레이드오프 인정 + "식별자만 가리고 판단에 필요한 속성(연령대·질병분류코드)은 남기는 식으로 최소화의 기준을 업무별로 정해야 한다".

## 4-3. 설명가능성 문단

> **원문**
> 둘째, 설명가능성 확보를 위해 RAG의 출처(Citation)를 답변에 명시하고 참조 문서를 추적 가능하게 만들어야 합니다. 저는 단순 벡터 검색 대신 Neo4j 기반 GraphRAG 및 온톨로지를 활용해 근거 문서와 관계를 함께 반환하도록 설계한 경험이 있으며, 이는 금융 심사 결과의 투명성을 높이는 실질적인 방안이 됩니다.

**등장 키워드**: Citation · 추적 가능성 · 온톨로지 · 투명성

### 용어 정리 — 여기서 혼동하면 위험하다
**생성형 AI의 "설명가능성"은 전통 XAI와 다르다.** 이 구분을 말하면 확실히 앞선다.

| 구분 | 대상 | 기법 |
|---|---|---|
| **전통 XAI** | 예측 모델(신용평가, 사기탐지) | **SHAP, LIME**, 부분의존도(PDP), 대리모델, **WoE/스코어카드(해석가능 모델 자체)** |
| **생성형 AI 근거 제시** | LLM 답변 | **Citation/Grounding**, 근거 문장 인용, 검색 경로 노출, **Attribution 검증(답변이 실제 근거에 있는지 재확인)** |

> "LLM은 내부 가중치를 SHAP처럼 설명할 수 없으므로, **모델을 설명하는 대신 근거를 추적 가능하게 만드는 방향**으로 접근해야 합니다." — 이 한 문장이 이 섹션의 핵심.

### Citation 구현 수준 3단계
1. **문서 단위 출처** — "출처: 약관 3장" (가장 흔함, 검증 약함)
2. **문장 단위 인용 + 스팬 매핑** — 답변 문장 ↔ 근거 문장 대응
3. **사후 검증(Attribution/Faithfulness check)** — 별도 모델로 "이 문장이 근거에 실제로 있는가" 판정 → **RAGAS의 faithfulness**, NLI 기반 검증

### GraphRAG가 설명가능성에 주는 것
"왜 이 결론인가"를 **경로(path)** 로 보여줄 수 있다.
예: `[사고유형:추돌] -[유사]-> [사례#1123] -[적용]-> [약관 12조] -[결과]-> [지급]`
→ 심사자가 근거 사슬 전체를 눈으로 확인. 벡터 검색의 "유사도 0.83" 보다 훨씬 설득력 있다.

**예상 질문**
- **Q. Citation을 붙였는데 그 출처가 실제로 답변을 뒷받침하는지는 어떻게 보장하나요?** → **가장 좋은 질문.** 사후 검증(3단계) + 근거 없으면 답변 거부(abstain) 정책.
- **Q. 모르면 모른다고 하게 하려면?** → "컨텍스트에 없으면 답하지 말 것" 지시 + 검색 점수 임계값 미달 시 생성 자체를 차단 + 폴백 문구.
- **Q. SHAP은 아시나요?** → 전통 XAI로 구분해서 안다고 답할 것.

## 4-4. 모델 리스크 관리 문단

> **원문**
> 셋째, 모델 리스크 관리 차원에서는 환각 현상에 대비해 LLM 출력을 구조화된 스키마(Envelope)로 강제 검증하고, 실패 시 규칙 기반 템플릿으로 자동 폴백하는 안전장치를 구현해 운영했습니다. 여기에 금융권은 사람의 검토(Human-in-the-loop) 게이트와 편향 모니터링을 결합해야 합니다.

**등장 키워드**: 환각 · 스키마 강제 검증 · Human-in-the-loop · 편향 모니터링 · 모델 리스크 관리

### 환각(Hallucination) 대응 계층
```
1. 입력: 검색 품질 향상(하이브리드+리랭킹) — 근거가 좋아야 환각이 준다
2. 생성: 낮은 temperature, "컨텍스트 밖 답변 금지" 지시, 구조화 출력 강제
3. 검증: 스키마 검증 → 사실성 검증(faithfulness) → 금칙어/규정 위반 검사
4. 차단: 검증 실패 시 규칙 템플릿 폴백 또는 "확인 필요" 반환
5. 사람: 고위험 결정은 HITL 승인 게이트
6. 사후: 샘플링 감사, 사용자 피드백 루프
```
> **말할 문장**: "환각은 0으로 만들 수 없다는 전제에서, **환각이 사용자에게 도달하는 경로를 막는 설계**로 접근해야 합니다."

### Human-in-the-loop (HITL)
- **설계 포인트**: 어떤 결정에 게이트를 걸 것인가(임계값), 검토자에게 무엇을 보여줄 것인가(근거·신뢰도), 검토 결과를 어떻게 학습에 되먹일 것인가.
- **자동화 수준**: Human-in-the-loop(사람이 승인) / on-the-loop(감시·개입 가능) / in-command(전체 통제). 보험 지급 심사는 최소 in-the-loop.
- **관련**: EU AI Act의 고위험 시스템 **인적 감독(human oversight)** 요구.

### 편향(Bias) / 공정성
| 지표 | 의미 |
|---|---|
| **Demographic Parity** | 집단별 긍정 판정 비율이 동일 |
| **Equal Opportunity** | 실제 자격자 중 긍정 판정 비율 동일 |
| **Equalized Odds** | TPR·FPR 모두 동일 |
| **Disparate Impact (4/5 rule)** | 집단 간 비율이 80% 미만이면 차별 소지 |

> **금융 특유의 함정**: 성별·연령을 직접 안 써도 **대리변수(proxy)** — 거주지, 직업, 가입채널 — 를 통해 간접 차별이 발생한다. 이 단어를 쓰면 깊이가 드러난다.
> **도구**: Fairlearn(MS), AIF360(IBM), Azure AI Foundry 평가 기능.

### 모델 리스크 관리 = MLOps/LLMOps 실무
- **모델 인벤토리**: 어떤 모델이 어디서 무슨 목적으로 쓰이는지 목록화 (금융 모범규준의 출발점)
- **검증(Validation)**: 개발자와 **독립된 조직**의 검토 — 금융권 핵심 원칙
- **주기적 재검증**: 모델·데이터 드리프트 감시
- **드리프트**: Data drift(입력 분포 변화), Concept drift(입력-정답 관계 변화)
- **회귀 평가**: 프롬프트/모델 변경 시 골든셋으로 CI 자동 평가 (**LLM판 회귀 테스트**)
- **섀도 배포 / 카나리**: 신모델을 실제 트래픽에 반영 없이 병행 실행 후 비교

**예상 질문**
- **Q. 모델이나 프롬프트를 바꿨을 때 기존 답변 품질이 나빠진 걸 어떻게 아나요?** → 골든셋 회귀 평가. **자소서에 없는 구멍이므로 반드시 준비.**
- **Q. AI가 잘못된 심사 결과를 냈다면 책임은 누구에게 있나요?** → 정답은 "AI는 도구이고 최종 책임은 운영 주체". 그래서 근거 기록·HITL·감사로그가 필수라고 연결.

## 4-5. 거버넌스 문단

> **원문**
> 마지막으로 내부통제 및 거버넌스를 위해, 프롬프트를 카탈로그와 DB 구조로 자산화하여 이력 추적 기반을 다진 경험이 있습니다. 이를 금융 환경에 확장하여 프롬프트·모델·데이터에 대한 권한 분리와 감사 로그, 변경 승인 절차를 제도화함으로써 규제 준수와 운영 안정성을 동시에 달성할 수 있습니다.

**등장 키워드**: 프롬프트 카탈로그 자산화 · 이력 추적 · 권한 분리 · 감사 로그 · 변경 승인 절차

### 프롬프트 자산화 = Prompt Registry / Prompt Versioning
**"프롬프트는 코드다"** 라는 관점. 물어볼 것들:

| 질문 | 답할 내용 |
|---|---|
| 버전 관리는? | DB 버전 컬럼 / Git / 전용 도구 |
| **롤백은 어떻게?** | **되물음 1순위.** 이전 버전 즉시 활성화 가능했는지 |
| 누가 바꿀 수 있나? | 권한 분리 — 개발자 vs 현업 vs 승인자 |
| 어떤 응답이 어떤 프롬프트 버전에서 나왔나? | **응답 로그에 prompt_version을 남겼는지** — 감사의 핵심 |
| 변경 전 검증은? | 골든셋 평가 후 승인 |

| 도구 | 설명 |
|---|---|
| **Langfuse Prompt Management** | 버전·라벨(prod/staging)·롤백·A/B. 오픈소스 |
| **LangSmith Prompt Hub / PromptLayer** | 상용 |
| **Git 기반 + 코드 리뷰** | 가장 단순하고 감사에 강함. 다만 현업이 못 고침 |
| **DB + 어드민(내가 한 것)** | 현업 편집 가능. **대신 코드리뷰·승인 절차를 어떻게 대체했는지가 질문** |

### 금융 내부통제 어휘 (이 단어들을 쓰면 "금융 준비된 사람"으로 보인다)
- **직무분리(SoD, Segregation of Duties)** — 개발자가 운영 데이터에 직접 접근 못하게
- **최소권한(PoLP)** · **4-eyes principle**(2인 승인)
- **변경관리(Change Management)** — 요청→검토→승인→배포→사후검증, 긴급변경 사후승인
- **감사증적(Audit Trail)** — 누가·언제·무엇을·왜. **위변조 방지(append-only, WORM 스토리지)**
- **로그 보존기간** — 전자금융감독규정상 보존 의무

| **Contextual Retrieval** | 청크 앞에 문서 맥락 요약을 붙여 인덱싱 |
| **TPM / RPM** | Azure OpenAI 분당 토큰/요청 쿼터. 429의 원인 |
| **PTU** | 처리량 예약 방식 배포. 쿼터 안정성이 필요할 때 |
| **Retry-After** | 429 응답에 담기는 재시도 대기시간 헤더 |
| **지수 백오프 + Full Jitter** | 재시도 간격을 늘리고 무작위화해 동시 재시도 폭주 방지 |
| **토큰 버킷 / 리키 버킷** | 버스트 허용형 / 출력 평탄화형 레이트 리밋 |
| **백프레셔** | 큐가 차면 상류에 압력을 전달해 유입을 줄임 |
| **Fair Queuing** | 사용자별 큐를 라운드로빈해 기아와 head-of-line blocking 방지 |

| **멱등키** | 재시도 시 중복 처리를 막는 요청 식별자 |
| **p95 / p99** | 상위 5%/1% 지연. 평균이 감추는 꼬리를 본다 |
| **가명처리 vs 익명처리** | 추가정보로 복원 가능 / 복원 불가(개보법 적용 제외) |
| **Private Endpoint** | 퍼블릭 인터넷을 경유하지 않는 사설 접근 지점 |
| **프롬프트 인젝션** | 입력·문서에 숨긴 지시로 시스템 프롬프트를 무력화하는 공격 |
| **Faithfulness** | 답변이 제공된 근거에 실제로 기반하는 정도 |
| **SHAP / LIME** | 예측 모델의 피처 기여도를 설명하는 전통 XAI 기법 |
| **HITL** | 고위험 결정에 사람 승인 게이트를 두는 것 |
| **Disparate Impact (4/5 rule)** | 집단 간 긍정률 비가 80% 미만이면 차별 소지 |
| **Proxy 변수** | 보호속성을 직접 안 써도 간접 차별을 유발하는 대리 변수 |
| **드리프트** | 입력 분포(Data) 또는 입력-정답 관계(Concept)의 변화 |
| **모델 인벤토리** | 사내 모든 모델의 목적·소유자·리스크 등급 목록 |
| **직무분리(SoD)** | 개발·운영·승인 권한을 분리해 단독 통제 불가하게 |
| **Audit Trail** | 누가·언제·무엇을·왜 했는지의 위변조 불가 기록 |
