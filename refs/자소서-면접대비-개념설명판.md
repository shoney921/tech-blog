## 1-2. 이 그림에서 가장 중요한 한 가지

**진단 엔진(FSM)과 LLM 연동 레이어가 분리되어 있다는 것.**

이걸 왜 그렇게 강조하냐면 —

```
[나쁜 구조]                         [내가 만든 구조]
사용자 → LLM → 사용자              사용자 → FSM(흐름 결정) → LLM(문장 생성) → 사용자
        ↑                                  ↑
   LLM이 흐름도 결정                   흐름은 코드가 결정
   → LLM 죽으면 서비스 정지            → LLM 죽어도 흐름은 살아있음
   → 매번 다른 길로 감                 → 항상 같은 길
   → 어디서 뭘 물었는지 추적 불가       → 로그로 완벽 추적
```

**면접에서 이 그림 하나만 제대로 설명해도 절반은 간다.** 나머지 챕터는 이 그림의 각 박스를 확대한 것이다.

# 2장. LLM의 본질 — 왜 LLM은 거짓말을 하는가

> 이 장을 이해하면 3장(왜 흐름을 맡기면 안 되나), 4장(왜 RAG가 필요한가), 10장(왜 환각을 못 없애나)이 전부 자동으로 이해된다.

## 2-1. LLM은 "다음 단어를 찍는 기계"다

### 한 문장 정의
LLM은 지금까지의 텍스트를 보고 **다음에 올 토큰의 확률분포**를 계산해서 하나를 뽑는 것을 반복하는 모델이다. 그 이상도 이하도 아니다.

### 동작 그림
```
입력: "대한민국의 수도는"

모델이 계산한 다음 토큰 확률:
  "서울"   ████████████████████ 92%
  " 서울"  ███ 4%
  "부산"   █ 1.2%
  "어디"   █ 0.8%
  ... (나머지 수만 개 토큰에 남은 확률 분산)

→ 확률에 따라 하나를 뽑음 → "서울"
→ 이제 입력이 "대한민국의 수도는 서울" 이 되고, 다시 다음 토큰 계산
→ 반복
```

### 왜 이게 중요한가
**모델은 "사실"을 저장한 DB가 아니다.** 학습 데이터에서 "대한민국의 수도는" 다음에 "서울"이 자주 나왔기 때문에 확률이 높은 것뿐이다.

그래서 —
- 학습 데이터에 없던 것(사내 규정, 최근 뉴스)은 **그럴듯하게 지어낸다** → **환각(Hallucination)**
- 확률이 애매하면 **매번 다른 답이 나온다** → **비결정성**

> **면접 문장**: "LLM은 지식 데이터베이스가 아니라 확률적 생성기입니다. 그래서 환각은 버그가 아니라 작동 원리의 부산물이고, **없애는 게 아니라 통제하는 대상**입니다."

## 2-2. 토큰 (Token)

### 한 문장 정의
LLM이 글자를 다루는 **최소 단위**. 단어보다 작고 글자보다 크다.

### 감각 잡기
```
영어: "unbelievable" → ["un", "bel", "iev", "able"]  (4토큰)
한국어: "안녕하세요"  → ["안", "녕", "하", "세", "요"] 정도  (5토큰)

대략적 감각 (모델마다 다름):
  영어 1토큰 ≈ 0.75단어 ≈ 4글자
  한국어 1토큰 ≈ 1~1.5글자   ← 한국어가 토큰을 훨씬 많이 먹는다!
```

### 왜 중요한가
1. **돈이 토큰 단위로 나간다.** 입력 토큰 × 단가 + 출력 토큰 × 단가.
2. **쿼터(TPM)가 토큰 단위다.** → 6장 429 에러의 직접 원인.
3. **한국어는 영어보다 2~3배 비싸다.** 같은 내용도 토큰이 더 많이 든다.

> **면접에서 써먹을 디테일**: "한국어는 토크나이저 효율이 낮아서 같은 분량이라도 영어 대비 토큰이 2~3배 나옵니다. 그래서 프롬프트에 넣을 컨텍스트 양을 정할 때 영어 기준 감각으로 잡으면 쿼터가 훨씬 빨리 찹니다."

## 2-3. 컨텍스트 윈도우 (Context Window)

### 한 문장 정의
모델이 **한 번에 볼 수 있는 토큰의 총량**. 입력 + 출력을 합친 한도.

### 비유
**책상 크기**다. 아무리 똑똑해도 책상에 못 올린 자료는 참고할 수 없다.

```
컨텍스트 윈도우 128,000 토큰인 모델의 예산 배분:

┌──────────────────────────────────────────────┐
│ 시스템 프롬프트          2,000 토큰           │
│ 대화 이력               8,000 토큰           │
│ RAG로 가져온 검색 문서   20,000 토큰    ← 여기가 문제  │
│ 사용자 질문               500 토큰           │
│ ────────────────────────────────             │
│ 남은 출력 여유          97,500 토큰           │
└──────────────────────────────────────────────┘
```

### 왜 중요한가
- **대화가 길어지면 이력이 컨텍스트를 다 먹는다** → 요약하거나 잘라내야 함(내 프로젝트의 "LLM 요약 배치"가 이런 맥락)
- **"Lost in the middle" 현상**: 컨텍스트 가운데 있는 정보를 모델이 잘 놓친다. 그래서 검색 결과를 그냥 많이 넣는 게 답이 아니라 **적게, 정확하게** 넣어야 한다 → 4장 리랭킹의 존재 이유

> **흔한 오해**: "컨텍스트가 커졌으니 RAG는 이제 필요 없다"
> **반박**: ①비용이 토큰에 비례해 폭증 ②Lost in the middle로 정확도가 오히려 떨어짐 ③사내 문서 전체는 여전히 128k에 안 들어감 ④근거 추적(Citation)이 안 됨

## 2-4. Temperature / Top-p — 무작위성 조절 손잡이

### 그림으로 이해
```
Temperature = 0.0  (거의 결정적)
  "서울" ████████████████████████████ 99.9%
  → 사실상 항상 "서울"

Temperature = 1.0  (기본)
  "서울" ████████████████████ 92%
  "부산" █ 1.2%
  → 대체로 "서울", 아주 가끔 다른 것

Temperature = 2.0  (창의적/무질서)
  "서울" ██████████ 45%
  "부산" ██████ 20%
  "제주" ████ 12%
  → 뭐가 나올지 모름
```

**temperature는 확률분포를 평평하게(높게) 또는 뾰족하게(낮게) 만드는 값**이다.
**top-p(nucleus sampling)** 는 다른 방식: 확률 높은 순으로 누적 p%까지만 후보로 남기고 나머지는 버린다.

### 내 프로젝트에서의 판단
진단 서비스처럼 **일관성이 중요한 곳은 temperature를 낮게**. 반대로 아이디어 브레인스토밍은 높게.

> **면접 질문 대비**: "temperature 0으로 하면 완전히 같은 답이 나오나요?"
> **정답**: "이론상 가장 확률 높은 토큰만 고르지만, **실무에서 100% 재현은 보장되지 않습니다.** GPU 부동소수점 연산 순서, 배칭, 백엔드 버전에 따라 미세한 차이가 생깁니다. 그래서 **재현성이 필요하면 모델이 아니라 시스템 설계(FSM)에서 확보해야 한다**는 게 제 결론이었습니다."
> ↑ **이 답변이 자소서의 FSM 설계와 완벽하게 연결된다. 강력한 답이다.**

## 2-5. 환각(Hallucination)이 생기는 3가지 경로

| 경로 | 설명 | 예시 | 대응 |
|---|---|---|---|
| **지식 공백** | 학습 데이터에 없는 것을 확률로 메움 | 사내 규정 조항 번호를 지어냄 | **RAG** (근거를 넣어줌) |
| **근거 무시** | 근거를 줬는데도 자기 지식으로 답함 | 문서엔 3년인데 5년이라 답함 | Faithfulness 검증, 프롬프트 강화 |
| **형식 강제** | "무조건 답하라"는 압박에 없는 답을 만듦 | "모른다"고 못 하게 설계된 프롬프트 | **거부(abstain) 경로 허용** |

> **핵심 통찰**: 세 번째가 의외로 많다. **"모르면 모른다고 답해도 된다"는 출구를 만들어주지 않으면 모델은 반드시 지어낸다.**

# 3장. 대화 흐름 제어 — 상태기계, 슬롯, Envelope

## 3-1. 왜 LLM에게 흐름을 맡기면 안 되는가

### 실패 시나리오로 이해하기

**LLM에게 흐름을 맡긴 경우:**
```
사용자 A: "매출은 100억 정도입니다"
  LLM: "직원 수는 어떻게 되나요?"        ← 2번 질문으로 감

사용자 B: "매출은 100억 정도입니다"      ← 똑같은 답변인데
  LLM: "그럼 주력 사업은 무엇인가요?"     ← 5번 질문으로 감!

→ 두 사람의 진단 결과가 다르다. 왜? 아무도 모른다.
→ "진단"이라는 이름을 붙일 수 없다.
```

**FSM으로 흐름을 통제한 경우:**
```
사용자 A: "매출은 100억 정도입니다"
  코드: slot["매출"] 채워짐 → 단계2의 필수슬롯 3개 중 3개 완료 → 단계3으로
  LLM: (단계3용 질문을 "문장으로만" 생성)

사용자 B: 동일 입력 → 동일 경로. 100%.
```

## 3-2. 유한 상태기계(FSM) 완전 이해

### 한 문장 정의
**"지금 어느 칸에 있고, 무슨 조건이면 어느 칸으로 옮겨가는지"** 를 미리 다 그려놓은 것.

### 비유
**보드게임 판**이다. 말이 놓인 칸(State)이 있고, 주사위 결과(Event)에 따라 정해진 칸으로 이동한다. 말이 어디로 갈지는 **판이 결정**하지, 말이 결정하지 않는다.

### 4개 부품

| 부품 | 뜻 | 내 진단 서비스 예시 |
|---|---|---|
| **State (상태)** | 지금 있는 칸 | `기업개요_수집`, `현황진단`, `과제도출`, `산출물생성` |
| **Slot (슬롯)** | 그 칸에서 채워야 할 빈칸 | 기업개요 단계 → `업종`, `매출규모`, `직원수` |
| **Transition (전이)** | 칸 → 칸 이동 | 기업개요 완료 → 현황진단 |
| **Guard (가드)** | 이동해도 되는지 검사하는 문지기 | "필수 슬롯 3개가 모두 채워졌는가?" |

### 코드로 보면 이런 느낌
```python
STATES = {
    "기업개요_수집": {
        "required_slots": ["업종", "매출규모", "직원수"],
        "next": "현황진단",
    },
    "현황진단": {
        "required_slots": ["현재_AI활용도", "주요_페인포인트"],
        "next": "과제도출",
    },
    # ...
}

def step(session, user_input):
    state = STATES[session.current_state]

    # 1. LLM에게 "이 답변에서 슬롯을 추출해줘" 요청 (콘텐츠 레이어)
    extracted = llm.extract_slots(user_input, state["required_slots"])
    session.slots.update(extracted)

    # 2. 가드: 흐름 판단은 코드가 한다 (결정적)
    missing = [s for s in state["required_slots"] if not session.slots.get(s)]

    if missing:
        # 3. Probe: 부족한 축만 다시 물어본다
        return llm.generate_probe(missing)      # ← 여기가 "부족한 축만 재질의"
    else:
        session.current_state = state["next"]   # ← 전이
        return llm.generate_question(session.current_state)
```

> **이 코드 흐름을 말로 설명할 수 있으면 1부 방어는 끝난다.**
> 포인트: **`missing` 계산은 파이썬이 한다. LLM은 문장만 만든다.** 이게 "분리"의 실체다.

### 흔한 오해
- **오해**: "FSM은 옛날 기술 아닌가요?"
- **답변**: "오래된 만큼 검증된 기술이고, **재현성과 감사 가능성이 요구되는 도메인에서는 여전히 정답**입니다. 실제로 LangGraph도 본질은 그래프 형태의 상태기계입니다. 최신 프레임워크들이 다시 상태기계로 돌아온 이유가 있다고 봅니다."

## 3-3. 슬롯 필링 (Slot Filling)

### 비유
**서류 양식 채우기**다. 창구 직원이 "성함이요? 생년월일이요? 주소요?" 하고 빈칸을 채워가는 것.

### 3가지 판단 방식 (면접 단골)

```
[방식 A] LLM이 판단
  입력: "저희 회사는 그냥 좀 크죠"
  LLM: "매출규모 슬롯 → 미충족 (구체적 수치 없음)"
  장점: 뉘앙스를 잡음    단점: 판단이 매번 흔들림, 판단 자체가 환각 가능

[방식 B] 규칙이 판단
  if len(answer) > 10 and re.search(r'\d+', answer): 충족
  장점: 빠르고 결정적    단점: "1234"만 써도 통과

[방식 C] 하이브리드 ★실무 정답
  1차: 규칙으로 명백한 것 컷 (빈 문자열, 너무 짧음)
  2차: 애매한 것만 LLM에 판정 요청
  → 비용 절감 + 정확도 확보
```

### 무한 루프 방지 — 반드시 준비할 답변
```
Probe 횟수를 세션에 기록:
  probe_count[slot] += 1
  if probe_count[slot] >= 2:
      slots[slot] = "미상"     # 부분 정보로 진행
      다음 단계로 전이
```
> **면접 문장**: "사용자가 계속 성의 없이 답하면 무한 재질의에 빠질 수 있어서, **슬롯당 재질의 상한을 두고 넘으면 '미상'으로 기록한 뒤 진행**하도록 했습니다. 완주율이 진단 품질보다 우선이라고 판단했습니다."

## 3-4. Envelope = 구조화 출력

### 왜 필요한가 — 실패로 이해하기

```
[구조화 없이]
LLM 응답: "좋습니다! 다음으로 매출 규모를 알려주세요. 100억 미만인가요, 이상인가요?"

프론트엔드 개발자: "...선택지 버튼은 어떻게 만들죠?"
백엔드 개발자: "...지금 몇 단계인지는 어떻게 알죠?"
→ 문자열 파싱 지옥 시작
```

```
[Envelope로]
{
  "message": "좋습니다! 다음으로 매출 규모를 알려주세요.",
  "choices": [
      {"id": "under_100", "label": "100억 미만"},
      {"id": "over_100",  "label": "100억 이상"},
      {"id": "etc",       "label": "직접 입력"}
  ],
  "stage": {"current": "기업개요_수집", "index": 2, "total": 6},
  "slots": {"업종": "제조", "매출규모": null, "직원수": 120}
}
→ 프론트는 이 JSON만 렌더링하면 끝
→ 백엔드는 slots만 보고 다음 흐름을 판단
```

### 4가지 구현 방식 — 보장 강도 순서

```
1) 프롬프트로 부탁              "JSON으로 답해줘"
   보장: 없음. 앞에 "네, 알겠습니다!"를 붙여버림 → 파싱 실패
   대응: 정규식으로 { } 추출 + 실패 시 재시도

2) JSON mode                    response_format={"type": "json_object"}
   보장: 유효한 JSON임은 보장
   한계: 필드 이름이 다르거나 빠져도 통과함

3) Structured Outputs           response_format={"type":"json_schema", "strict": true}
   보장: 내가 정의한 스키마를 100% 준수
   원리: ↓ 아래 설명

4) Function/Tool Calling        함수 인자로 스키마 강제
   보장: 높음. 원래 용도는 "도구 호출"이지만 구조화 출력에도 널리 쓰임
```

### Structured Outputs가 100%를 보장하는 원리 — 제약 디코딩(Constrained Decoding)

**이걸 설명할 수 있으면 상위 5%다.**

```
LLM은 매 스텝마다 "다음 토큰 후보 5만 개"에 확률을 매긴다.
제약 디코딩은 그 확률 위에 마스크를 씌운다.

현재까지 생성: {"message": "안녕하세요"

스키마상 다음에 올 수 있는 것: , 또는 }
→ 그 외 49,998개 토큰의 확률을 강제로 0으로 만든다(마스킹)
→ 문법적으로 틀린 출력이 "생성 자체가 불가능"해진다

이게 "재시도로 맞추는 것"과 "구조적으로 보장하는 것"의 차이다.
```

> **면접 문장**: "프롬프트로 JSON을 부탁하는 건 확률에 기대는 거고, Structured Outputs는 디코딩 단계에서 스키마 밖 토큰을 마스킹해서 **구조적으로 위반이 불가능하게** 만드는 겁니다. 저희는 당시 API 버전 문제로 검증+재시도 방식이었는데, 지금이면 strict 스키마를 씁니다."

### 검증 실패 시 처리 흐름
```
LLM 응답
   ↓
Pydantic 스키마 검증 ─── 성공 ──→ 사용
   ↓ 실패
재시도 (에러 메시지를 프롬프트에 되먹임)   ← "이 필드가 빠졌다"고 알려주면 성공률↑
   ↓ 또 실패 (N회)
규칙 기반 템플릿 폴백  ← 미리 써둔 문장 + 슬롯 값 치환
   ↓
사용자는 서비스가 멈춘 걸 모른다
```

## 3-5. 폴백 (Graceful Degradation)

### 비유
**엘리베이터가 고장 나도 계단이 있다.** 불편하지만 건물 밖으로는 나갈 수 있다.
반대말은 **단일 실패 지점(SPOF)** — 엘리베이터만 있는 건물.

### 폴백 5단계 (내 시스템 기준)
```
1차  기본 모델 호출
      ↓ 실패(429/타임아웃/5xx)
2차  재시도 — Retry-After 존중 + 지수 백오프 + 지터
      ↓ 계속 실패
3차  대체 리소스/모델로 라우팅 (모델 스위처)
      ↓ 그것도 실패
4차  규칙 기반 템플릿 응답
      "귀사의 {업종} 특성상 다음 항목을 점검해 보시기 바랍니다: ..."
      ↓ 최악
5차  진행 상태 저장 + "잠시 후 이어서 진행" 안내
```

### 서킷 브레이커 (Circuit Breaker)

**비유**: 집의 **두꺼비집(누전 차단기)**. 계속 스파크가 튀면 아예 전기를 끊어버린다.

```
상태 3개:
  CLOSED (정상)   → 호출 통과. 실패를 카운트.
     │ 연속 5회 실패
     ▼
  OPEN (차단)     → 호출 자체를 안 함. 즉시 폴백. (30초 유지)
     │ 30초 경과
     ▼
  HALF_OPEN (탐색) → 딱 1건만 시험 통과
     ├─ 성공 → CLOSED로 복귀
     └─ 실패 → 다시 OPEN
```

**왜 필요한가**: 이미 죽은 API에 계속 요청을 보내면 ①상대 서버 복구를 방해하고 ②우리 스레드/커넥션이 타임아웃 대기로 다 묶여서 **정상 기능까지 죽는다**(장애 전파).

> **면접 대비**: 자소서에 서킷 브레이커가 없다. 물어보면 —
> "정식 서킷 브레이커는 없었고, **재시도 상한과 큐 길이 제한으로 사실상의 백프레셔**를 걸었습니다. 다만 이미 실패 중인 API를 계속 때린 건 맞고, 개선 항목으로 봤습니다."

### 벌크헤드 (Bulkhead)

**비유**: **선박의 격벽**. 배 밑에 구멍이 나도 그 칸만 물이 차고 배 전체는 안 가라앉는다.

내 프로젝트의 **"Azure OpenAI를 Chat용/이미지용 리소스로 물리적 분리"** 가 정확히 이것이다.
```
[분리 전]                      [분리 후]
 하나의 리소스                  Chat 리소스     이미지 리소스
 쿼터 공유                      쿼터 독립       쿼터 독립
    │                             │              │
 이미지가 쿼터 다 씀            이미지 폭주      Chat은 멀쩡
    ↓                                            ↓
 채팅도 429 → 서비스 전체 마비                  대화는 계속 진행 가능
```

# 4장. 검색(RAG) — 임베딩부터 리랭킹까지

## 4-1. 왜 RAG인가 — 3가지 선택지 비교

모델이 모르는 지식을 알게 하는 방법은 3개뿐이다.

```
[방법 1] 파인튜닝 — 모델 자체를 다시 학습시킨다
  비유: 신입사원을 재교육시켜 머리에 넣는다
  장점: 말투/형식/도메인 스타일을 체화
  단점: 지식이 바뀌면 재학습, 비쌈, 근거 추적 불가, 최신성 없음
  → "무엇을 아는가"보다 "어떻게 말하는가"에 적합

[방법 2] 롱 컨텍스트 — 그냥 다 프롬프트에 넣는다
  비유: 신입사원에게 매번 매뉴얼 전체를 통째로 들려준다
  장점: 단순
  단점: 비용 폭증, Lost in the middle, 애초에 사내문서 전체는 안 들어감

[방법 3] RAG — 질문에 필요한 부분만 찾아서 넣어준다  ★
  비유: 신입사원 옆에 사서를 붙여준다. 질문할 때마다 해당 페이지만 뽑아줌
  장점: 최신 반영 즉시, 근거 추적(Citation) 가능, 비용 효율
  단점: 검색이 틀리면 답도 틀림 (Garbage In, Garbage Out)
```

> **면접 문장**: "파인튜닝은 '말하는 방식'을, RAG는 '아는 내용'을 다루는 도구라고 봅니다. 규정처럼 자주 바뀌고 **근거를 제시해야 하는 지식은 RAG가 맞고**, 파인튜닝은 출력 형식이나 도메인 어투를 고정할 때 씁니다. 금융권이면 특히 근거 추적 때문에 RAG가 기본이어야 합니다."

## 4-2. RAG 전체 파이프라인

```
[사전 작업 — 인덱싱 (한 번, 또는 문서 갱신 시)]
문서 → ①청킹 → ②임베딩 → ③벡터DB 저장 + 키워드 인덱스 저장

[질의 시 — 런타임 (매 요청)]
질문 → ④질문도 임베딩 → ⑤검색(벡터 + 키워드) → ⑥융합(RRF)
     → ⑦리랭킹 → ⑧프롬프트 조립 → ⑨LLM 생성 → ⑩Citation 부착
```

각 번호마다 "왜 그렇게 했나"를 물어볼 수 있다. 아래에서 하나씩 본다.

## 4-3. 임베딩(Embedding) — 의미를 숫자로

### 한 문장 정의
텍스트를 **의미가 비슷하면 가까운 위치에 놓이는 숫자 배열(벡터)** 로 바꾸는 것.

### 비유
**지도 위의 좌표**다. 서울과 인천은 가깝고, 서울과 부산은 멀다. 마찬가지로 "강아지"와 "개"는 벡터 공간에서 가깝고, "강아지"와 "회계감사"는 멀다.

### 그림으로
```
2차원으로 줄여서 상상하면 (실제로는 1536차원 같은 고차원):

        ↑
        │      · 고양이
        │   · 강아지        · 애완동물
        │ · 개
        │
        │                          · 보험금
        │                        · 지급심사
        │                     · 약관
        └────────────────────────────────→

"멍멍이"를 임베딩하면 → 강아지/개 근처에 찍힌다
→ 단어가 달라도(키워드가 안 겹쳐도) 찾아낼 수 있다  ★이게 벡터 검색의 힘
```

### 유사도 계산 — 코사인 유사도
```
두 벡터 사이의 "각도"를 본다. 길이는 무시.

cos(θ) = (A · B) / (|A| × |B|)

 1.0  = 완전히 같은 방향 (의미가 거의 동일)
 0.0  = 직교 (무관)
-1.0  = 반대 방향

실무에서는 보통 0.7~0.9 사이가 "관련 있음" 구간인데,
★ 이 임계값은 모델마다/도메인마다 달라서 반드시 실측해야 한다.
```

> **면접 질문**: "유사도 임계값은 얼마로 두셨나요?"
> **좋은 답**: "절대 임계값보다 **상위 k개를 뽑고 리랭커로 거르는 방식**을 썼습니다. 코사인 값의 절대 크기는 임베딩 모델이 바뀌면 의미가 달라져서 고정 임계값은 위험하다고 봤습니다." (임계값을 썼다면 그 값과 결정 근거를 말할 것)

### 알아둘 임베딩 모델
| 모델 | 차원 | 비고 |
|---|---|---|
| `text-embedding-3-small` | 1536 | 가성비. Azure OpenAI |
| `text-embedding-3-large` | 3072 | 정확도↑, 비용·저장↑ |
| `bge-m3`, `multilingual-e5` | 1024 | 오픈모델, 한국어 강함, **온프렘 가능** |
| `KURE`, `KoSimCSE` 등 | - | 한국어 특화 |

> **금융권 포인트**: 임베딩도 결국 **텍스트를 외부 API로 보내는 것**이다. 폐쇄망이면 임베딩 모델도 온프렘이어야 한다. 이걸 언급하면 감각 있어 보인다.

## 4-4. 벡터 검색의 원리 — ANN과 HNSW

### 문제
문서 청크가 100만 개면, 질문 벡터와 100만 개를 전부 비교(brute force)해야 하나? → 너무 느리다.

### 해결: 근사 최근접 이웃 (ANN, Approximate Nearest Neighbor)
**정확도를 아주 조금 포기하고 속도를 수백 배 얻는다.**

### HNSW — 가장 널리 쓰이는 ANN 알고리즘
```
비유: 전국 지도를 여러 축척으로 겹쳐 놓은 것

Layer 2 (전국 고속도로망 — 노드 적음)
   서울 ────────── 대전 ────────── 부산
    │               │               │
Layer 1 (국도)
   서울─수원─천안─대전─대구─울산─부산
    │
Layer 0 (모든 골목길 — 전체 노드)
   ...촘촘한 전체 그래프...

검색 방법:
  1) 맨 위 층에서 대충 목적지 방향으로 이동 (몇 번 만에 근처 도착)
  2) 한 층 내려가서 더 정밀하게
  3) 맨 아래 층에서 최종 이웃 확정
→ 100만 개를 다 안 봐도 됨
```

**튜닝 파라미터**: `M`(노드당 연결 수), `ef_construction`(인덱싱 정밀도), `ef_search`(검색 정밀도).
→ **ef_search를 올리면 정확도↑ 속도↓**. 전형적인 트레이드오프 손잡이.

> **면접 디테일**: "벡터 검색은 정확한 검색이 아니라 **근사 검색**이라 recall이 100%가 아닙니다. HNSW의 ef_search 같은 파라미터로 정확도와 지연을 맞바꾸는 구조라는 걸 이해하고 튜닝해야 합니다."

## 4-5. BM25 — 키워드 검색의 원리

### 한 문장 정의
**"이 단어가 이 문서에 얼마나 자주 나오는가(TF)"** 와 **"이 단어가 전체 문서에서 얼마나 희귀한가(IDF)"** 를 곱해서 점수를 매기는 고전 알고리즘.

### 직관
```
질문: "삼성전자 배당금 지급일"

"의", "를", "은" → 모든 문서에 다 나옴 → IDF 낮음 → 거의 무시
"배당금"          → 일부 문서에만    → IDF 높음 → 중요
"삼성전자"        → 더 희귀          → IDF 더 높음 → 가장 중요

+ 그 단어가 문서 안에서 자주 나올수록 점수↑ (단, 무한정 오르진 않음 = 포화)
+ 문서가 길수록 점수를 깎음 (긴 문서가 유리해지는 걸 방지 = 길이 정규화)
```

**BM25가 TF-IDF보다 나은 점**: ①TF 포화(같은 단어 100번 나온다고 100배 중요하진 않음) ②문서 길이 정규화. 파라미터 `k1`(포화 정도), `b`(길이 정규화 강도).

### 벡터 검색이 못 하는 것을 BM25가 한다
```
질문: "KC-2024-117 시험 결과"

벡터 검색: "KC-2024-117"은 학습 때 본 적 없는 문자열
          → 임베딩이 의미 없는 좌표에 찍힘 → 엉뚱한 문서 반환

BM25:     "KC-2024-117"이 정확히 들어있는 문서를 즉시 찾음  ★
```

**반대로**:
```
질문: "차 사고 났을 때 보상"
문서: "자동차 충돌 시 배상 절차"

BM25:  겹치는 단어 0개 → 못 찾음
벡터:  의미가 가까움 → 찾아냄  ★
```

> **이 두 예시가 하이브리드 검색의 존재 이유 전부다. 이대로 말하면 된다.**

## 4-6. 하이브리드 검색과 RRF — 숫자로 이해하기

### 문제
벡터 점수는 0~1(코사인), BM25 점수는 0~30 같은 무제한 스케일. **그냥 더할 수 없다.**

### 해결책 1: RRF (Reciprocal Rank Fusion) — 점수를 버리고 "등수"만 쓴다

```
공식:  RRF점수(문서) = Σ  1 / (k + 순위)      (k는 보통 60)
                      각 검색기별

실제 계산 예시:
                벡터검색 순위   BM25 순위    RRF 점수
문서 A              1위           5위      1/61 + 1/65 = 0.01639 + 0.01538 = 0.03177  ★1위
문서 B              2위          20위      1/62 + 1/80 = 0.01613 + 0.01250 = 0.02863
문서 C             50위           1위      1/110 + 1/61 = 0.00909 + 0.01639 = 0.02548
문서 D              3위        (없음)      1/63              = 0.01587

→ 양쪽에서 고루 상위인 A가 1등.
→ 한쪽에서만 1등인 C는 밀림.
→ 점수 스케일을 아예 신경 쓸 필요가 없다.  ★이게 RRF의 핵심 장점
```

**k=60의 의미**: k가 크면 순위 차이의 영향이 완만해지고, 작으면 1등에 가중치가 확 쏠린다. 60은 원논문의 경험적 기본값.

### 해결책 2: 가중합 (Convex Combination)
```
최종점수 = α × 정규화(벡터점수) + (1-α) × 정규화(BM25점수)

장점: α를 조절해 도메인에 맞게 튜닝 가능 (전문용어 많으면 BM25 비중↑)
단점: 정규화 방식(min-max? z-score?)에 결과가 흔들림, 쿼리마다 최적 α가 다름
```

> **면접 답변 뼈대**: "저희는 [RRF/가중합]을 썼습니다. RRF는 점수 스케일 정규화가 필요 없어서 운영이 단순하고, 가중합은 도메인 특성에 맞춰 튜닝 여지가 큽니다. **평가 데이터셋이 없으면 α를 튜닝할 근거가 없어서 RRF가 안전한 기본값**이라고 봅니다."

## 4-7. 청킹 — 왜 자르고, 어떻게 자르나

### 왜 자르나 (3가지 이유)
1. **임베딩 모델 입력 한계** (보통 512~8192 토큰)
2. **정밀도** — 100페이지 문서 하나를 벡터 하나로 만들면 의미가 뭉개진다. "이 문서 전체의 평균적 의미"는 아무것도 안 가리킨다.
3. **컨텍스트 예산** — 필요한 부분만 넣어야 토큰이 절약된다

### 잘못 자르면 벌어지는 일
```
원문: "...보험금은 사고일로부터 30일 이내에 지급한다.
       단, 조사가 필요한 경우 60일까지 연장할 수 있다."

[나쁜 청킹 — 문장 중간에서 자름]
청크1: "...보험금은 사고일로부터 30일 이내에 지급한다. 단, 조사가"
청크2: "필요한 경우 60일까지 연장할 수 있다."

→ 청크1만 검색되면 LLM은 "무조건 30일"이라고 답한다.  ★단서 조항 유실 = 치명적 오답
```

### 전략별 정리
```
① 고정 크기 + 오버랩
   [========500토큰========]
                  [========500토큰========]
                  ↑ 50~100토큰 겹침 → 경계에서 잘린 내용을 양쪽이 나눠 가짐
   가장 단순. 기본값으로 시작하기 좋음.

② 재귀 분할 (Recursive)
   문단(\n\n)으로 자르기 시도 → 너무 크면 문장(.)으로 → 그래도 크면 단어로
   LangChain 기본. 대체로 무난.

③ 문서 구조 기반
   "제3조 (보험금의 지급)" 같은 헤딩 단위로 자름
   ★ 약관·규정·성적서처럼 구조가 뚜렷하면 이게 최선

④ 시맨틱 청킹
   문장별 임베딩을 만들어 의미가 확 바뀌는 지점에서 자름
   정확하지만 인덱싱 비용↑

⑤ Parent-Child (small-to-big)  ★추천
   검색용: 작은 청크(정밀 매칭)
   전달용: 그 청크가 속한 큰 부모 문단(충분한 맥락)
   → "정밀하게 찾고, 넉넉하게 준다"

⑥ Contextual Retrieval (Anthropic 제안)
   각 청크 앞에 "이 청크는 2024년 자동차보험 약관 중 지급 절차 부분이다" 같은
   맥락 문장을 LLM으로 생성해 붙인 뒤 임베딩
   → 검색 정확도 크게 향상, 인덱싱 비용은 증가
```

> **면접 질문 "청크 크기는 어떻게 정했나요?"에 대한 안전한 답**:
> "기본값(예: 512토큰/50 오버랩)에서 시작해서, **실패 사례를 모아 보니 단서 조항이 잘려나가는 케이스가 많아** 문서 구조 단위 분할로 바꿨습니다. 정량 실험보다는 실패 케이스 기반 조정이었다는 점은 한계로 인정합니다."

## 4-8. 리랭킹 — Bi-encoder vs Cross-encoder

### 왜 필요한가
벡터 검색은 **질문과 문서를 따로따로 임베딩해서 비교**한다. 빠르지만 정밀하진 않다.

```
[Bi-encoder = 벡터 검색]                [Cross-encoder = 리랭커]

질문 → [인코더] → 벡터A                 질문 + 문서 → [인코더] → 관련성 점수
문서 → [인코더] → 벡터B                          ↑
        벡터A · 벡터B = 유사도            둘을 "같이" 읽고 판단

특징: 문서는 미리 임베딩해둘 수 있음    특징: 매번 질문+문서 쌍으로 계산해야 함
      → 100만 건도 순식간              → 100만 건은 불가능
정확도: 보통                            정확도: 훨씬 높음
```

### 그래서 2단계로 쓴다
```
1단계 (Retrieval):  100만 건 → 벡터+BM25로 상위 50건   [빠름]
2단계 (Rerank):     50건 → 크로스인코더로 정밀 재정렬 → 상위 5건  [정확]
3단계 (Generation): 5건만 LLM 컨텍스트에 투입
```

**비유**: 서류전형(빠르게 많이 거름) → 면접(정밀하게 소수를 판단). 면접을 100만 명에게 할 순 없다.

| 리랭커 | 특징 |
|---|---|
| **Cohere Rerank** | API형, 다국어 성능 좋음 |
| **BGE-reranker / Jina Reranker** | 오픈모델 → **폐쇄망에서 쓸 수 있음** (금융권 답변용) |
| **LLM-as-reranker** | LLM에게 직접 순위 매기게 함. 비쌈, 느림 |

> **자소서에 리랭킹이 없다.** 물어보면 "리랭킹 단계를 두지 않고 하이브리드 융합 결과를 바로 썼습니다. 지금 개선한다면 크로스인코더 리랭커를 넣는 게 가장 비용 대비 효과가 큰 개선일 겁니다." — **개선 방향을 아는 것 자체가 점수다.**

## 4-9. RAG 평가 — 자소서 최대 구멍 메우기

### 두 층으로 나눠서 본다
```
[1층] 검색이 잘 됐나? (Retrieval)
  Recall@k   : 정답 문서가 상위 k개 안에 들어왔는가       ← 가장 중요
  Precision@k: 상위 k개 중 관련 있는 게 몇 개인가
  MRR        : 정답이 몇 등에 있었나의 역수 평균 (1등=1.0, 2등=0.5, 4등=0.25)
  nDCG       : 순위와 관련도 등급을 함께 반영한 지표

[2층] 답변이 잘 됐나? (Generation) — RAGAS 4대 지표
  Faithfulness      : 답변이 근거 문서에 실제로 있는 내용인가  ← 환각 측정
  Answer Relevancy  : 답변이 질문에 맞는 소리를 하고 있나
  Context Precision : 가져온 문서 중 쓸모없는 게 얼마나 섞였나
  Context Recall    : 정답에 필요한 문서를 다 가져왔나
```

### 골든 데이터셋이란
```
질문 / 정답 / 근거문서 3쌍을 사람이 만들어 놓은 것. 50~200건이면 시작 가능.

예)
{
  "question": "자동차 사고 시 보험금 지급 기한은?",
  "ground_truth": "사고일로부터 30일 이내, 조사 필요 시 60일까지 연장",
  "reference_docs": ["약관_제12조_청크3"]
}

이걸 만들어 두면:
  · 프롬프트를 바꿨을 때 품질이 떨어졌는지 자동 감지  (= 회귀 테스트)
  · 청크 크기·top-k·리랭커 유무를 실험으로 비교 가능
  · "정확도를 높였다"에 숫자를 붙일 수 있음
```

> **면접 정직 전략 (외워둘 것)**:
> "정량 평가 체계를 갖추지 못하고 도메인 전문가의 정성 검토에 의존했습니다. **이게 이 프로젝트에서 제가 꼽는 가장 큰 한계**입니다. 다시 한다면 골든셋 50건이라도 먼저 만들고 시작할 겁니다. 검색은 Recall@k, 생성은 faithfulness를 보고, 프롬프트 변경 시 회귀 평가를 CI에 붙이는 게 순서라고 봅니다."
> → **약점을 정확한 용어로 설명하는 사람은 약점이 있어도 신뢰를 얻는다.**

# 5장. 그래프와 GraphRAG

## 5-1. 그래프 데이터베이스란

### 한 문장 정의
데이터를 **점(노드)과 선(관계)** 으로 저장하고, **관계를 따라 걸어다니며(traversal)** 질의하는 DB.

### 관계형 DB와 비교 — 왜 그래프인가
```
질문: "이 물질과 유사한 조건에서 사고가 난 적 있는 다른 물질들"

[관계형 DB]
SELECT ... FROM 물질 A
JOIN 시험 B ON ...
JOIN 결과 C ON ...
JOIN 물질 D ON ...      ← 조인 4번
JOIN 사고 E ON ...      ← 조인 5번
→ 관계를 한 단계 더 타려면 JOIN이 하나씩 늘어난다
→ 깊이가 깊어질수록 성능이 급격히 나빠짐

[그래프 DB]
MATCH (a:물질 {name:'X'})-[:시험됨]->(t:시험조건)<-[:시험됨]-(b:물질)-[:유발]->(s:사고)
RETURN b, s
→ 관계를 "따라 걷는" 게 저장 구조 자체
→ 깊이가 늘어도 비용이 완만하게 증가 (index-free adjacency)
```

**핵심 용어**: **index-free adjacency** — 노드가 이웃 노드의 물리적 주소를 직접 들고 있어서, 인덱스 조회 없이 포인터를 따라가면 된다. 이게 그래프 DB가 다중 홉에 강한 이유.

## 5-2. Cypher — 그래프 질의어

**SQL이 표라면 Cypher는 그림을 그린다.** 문법이 실제로 화살표처럼 생겼다.

```cypher
MATCH (a:물질 {name: '에탄올'})-[:담김]->(c:용기)
WHERE c.재질 = 'PE'
RETURN c.규격, c.용량

읽는 법:
 (a:물질)        → 동그라미 = 노드, 라벨이 '물질'
 -[:담김]->      → 화살표 = 관계, 타입이 '담김'
 (c:용기)        → 또 다른 노드
= "에탄올이 담긴 용기 중 재질이 PE인 것"
```

## 5-3. LPG vs RDF — 이력서에 "비교 검토"라고 썼으므로 반드시

```
[LPG — Labeled Property Graph]  Neo4j가 쓰는 모델
  (물질:에탄올 {인화점: 13, CAS: "64-17-5"})
       -[:시험됨 {일자: "2025-03-01", 온도: 60}]->
  (시험:내열시험)
  ★ 노드에도 관계에도 속성을 붙일 수 있다  ← 이게 핵심 장점

[RDF — Resource Description Framework]  표준 시맨틱웹 모델
  모든 것이 <주어> <술어> <목적어> 3개 짜리(트리플)
  <에탄올> <시험됨> <내열시험>
  <에탄올> <인화점> "13"

  ★ 관계에 속성을 붙이려면? → reification(관계를 다시 노드로 만들기) 필요
  <시험사건001> <대상> <에탄올>
  <시험사건001> <시험종류> <내열시험>
  <시험사건001> <일자> "2025-03-01"
  <시험사건001> <온도> "60"
  → 트리플 4개로 늘어나고 질의도 복잡해짐
```

| 항목 | LPG (Neo4j) | RDF (트리플스토어) |
|---|---|---|
| 관계에 속성 | 직접 가능 ★ | reification 필요 |
| 질의어 | Cypher (직관적) | SPARQL (표준, 학습곡선 있음) |
| 표준화 | 벤더별 (GQL 표준화 진행 중) | W3C 표준 ★ |
| 추론(Reasoning) | 별도 구현 | OWL 리즈너로 자동 추론 ★ |
| 데이터 통합/연결 | 상대적 약함 | URI 기반 전역 식별 ★ |
| 개발 친화성 | 높음 ★ | 낮음 |

> **면접 답변 (이력서 근거 있음)**: "RDF는 표준화와 자동 추론에 강점이 있지만, 저희 도메인은 **시험 조건·측정값처럼 관계 자체에 속성을 붙여야 하는 데이터**가 많았습니다. RDF로 하면 reification 때문에 모델이 복잡해지고 질의도 어려워져서, 개발·운영 생산성을 보고 LPG(Neo4j)를 택했습니다. 다만 여러 조직의 온톨로지를 연결해야 하는 과제였다면 RDF를 봤을 겁니다."

## 5-4. 온톨로지(Ontology)란

### 한 문장 정의
어떤 도메인에 **무슨 개념이 있고, 개념들 사이에 어떤 관계와 규칙이 성립하는지**를 형식적으로 정의한 것. 쉽게 말해 **도메인의 문법책**.

### 스키마와 뭐가 다른가
```
[DB 스키마]   "이 테이블엔 이런 컬럼이 있다"          — 저장 형식의 정의
[온톨로지]    "물질은 용기에 담긴다. 용기는 재질을 갖는다.
               인화성 물질을 금속 용기에 담으면 정전기 위험이 있다."
              — 의미와 규칙의 정의. 추론이 가능하다 ★
```

### 보험 도메인 예시 (면접에서 응용해 말하기 좋음)
```
개념(Class):    계약자, 피보험자, 보험계약, 담보, 사고, 청구, 지급결정
관계:           계약자 -[체결]-> 보험계약 -[포함]-> 담보
                사고 -[유발]-> 청구 -[적용]-> 담보 -[근거]-> 약관조항
규칙:           "면책사유에 해당하면 지급하지 않는다"

→ 지급 심사 결과를 "경로"로 설명할 수 있게 된다:
   [청구#123] → [담보:상해입원] → [약관 제8조] → [지급]
   [청구#456] → [면책:음주운전] → [약관 제15조] → [부지급]  ← 근거가 눈에 보인다
```

## 5-5. GraphRAG — 두 가지 다른 것

**이 구분을 모르면 대화가 어긋난다.**

```
[A] 지식그래프 기반 RAG   ← 내가 한 것
    사람이 도메인 온톨로지를 설계 → 데이터를 그래프로 적재
    → 자연어 질문을 그래프 탐색(Cypher)으로 변환해 근거 회수
    강점: 정확한 도메인 구조, 근거가 명확
    비용: 설계 인건비, 스키마 변경 시 재작업

[B] Microsoft GraphRAG    ← 오픈소스 패키지 이름
    LLM이 문서에서 엔티티·관계를 자동 추출
    → 커뮤니티 탐지(Leiden 알고리즘)로 클러스터링
    → 각 커뮤니티의 요약을 LLM이 생성
    → Local Search(특정 엔티티 중심) / Global Search(전체 요약 기반)
    강점: 자동화, "이 문서 전체의 주제는?" 같은 전역 질문에 강함
    비용: 인덱싱 시 LLM 호출이 대량 발생 → 비쌈
```

> **면접 대비**: "GraphRAG 쓰셨다는데 MS 패키지 말씀이신가요?" 라고 물으면
> "아니요, **도메인 엔티티와 관계를 직접 온톨로지로 설계하고 Neo4j에 적재한 뒤 그 위에서 탐색하는 구조**였습니다. MS GraphRAG처럼 문서에서 그래프를 자동 생성하는 방식은 아니었습니다."

## 5-6. 벡터 RAG가 못 푸는 질문 — 구체 예시 3개

**이 3개가 GraphRAG를 도입한 정당화 전부다.**

```
① 다중 홉(Multi-hop) 질문
   "우리와 비슷한 규모의 제조업체가 겪은 AI 도입 실패 사례는?"
   벡터: "비슷한 규모"를 벡터로 표현할 수 없음 → 실패
   그래프: (우리회사)-[유사규모]->(기업들)-[겪음]->(실패사례)  → 2홉 탐색으로 해결

② 집계형 질문
   "전체 사례에서 가장 자주 등장한 위험요인 3개는?"
   벡터: top-k 5건만 보므로 "전체"를 알 수 없음 → 구조적으로 불가능
   그래프: COUNT + ORDER BY로 정확히 집계

③ 부정/존재 질문
   "아직 시험하지 않은 물질-용기 조합은?"
   벡터: "없는 것"은 검색이 안 됨 (검색은 있는 것만 찾는다)
   그래프: 모든 조합 - 시험된 조합 = 미시험 조합  ← 이력서의 CT 성적서 POC가 정확히 이것
```

> **말하는 법**: "벡터 검색은 **'비슷한 것'을 찾는 도구**입니다. '연결된 것', '전부 세어본 것', '없는 것'은 못 찾습니다. 그 세 종류의 질문이 업무상 중요해서 그래프를 도입한 겁니다."

## 5-7. Text2Cypher와 그 한계

```
사용자: "에탄올 관련 사고 사례 보여줘"
   ↓
LLM (스키마를 프롬프트로 받은 상태)
   ↓
MATCH (m:물질 {name:'에탄올'})-[:유발]->(a:사고) RETURN a

문제점:
 · 스키마가 크면 프롬프트에 다 못 넣음 → 스키마 요약/검색 필요
 · 라벨명·속성명을 LLM이 지어냄 → 실행 에러
 · 위험한 쿼리 생성 가능 (DELETE, 전체 스캔)
대응:
 · 읽기 전용 계정 + 쿼리 화이트리스트/검증
 · 실행 에러를 LLM에 되먹여 자가 수정(self-correction)
 · 자주 쓰는 패턴은 파라미터화된 템플릿으로 고정  ← 실무에서 가장 안전
```

> **면접 문장**: "Text2Cypher는 편하지만 **LLM이 스키마를 착각하면 조용히 틀린 답이 나옵니다.** 그래서 자주 쓰이는 질의 패턴은 템플릿으로 고정하고, 자유 질의는 읽기 전용 권한과 결과 검증을 붙이는 게 안전하다고 봅니다."

# 6장. 클라우드 · 모델 운영

## 6-1. Azure OpenAI의 구조 — 용어 계층

```
Azure 구독 (Subscription)
 └ 리소스 그룹 (Resource Group)
    └ Azure OpenAI 리소스 (= 엔드포인트 1개 + API 키)
       ├ 배포(Deployment) "my-gpt4o-chat"      ← 모델 gpt-4o,  TPM 100K 할당
       ├ 배포(Deployment) "my-gpt4o-mini"      ← 모델 gpt-4o-mini, TPM 200K
       └ 배포(Deployment) "my-embedding"       ← text-embedding-3-small

★ 호출할 때 모델명이 아니라 "배포 이름"을 넣는다. (OpenAI API와 가장 큰 차이)
★ 쿼터는 배포 단위로 할당된다.
```

**내 프로젝트의 "리소스 물리적 분리"란**:
```
리소스 A (Chat용)        엔드포인트 A, 키 A, 쿼터 A
리소스 B (이미지용)      엔드포인트 B, 키 B, 쿼터 B
→ B의 쿼터가 바닥나도 A는 무관 (벌크헤드)
→ 키가 분리되니 권한 최소화에도 유리 (금융 문항과 연결)
→ 비용도 리소스 단위로 분리 집계됨
```

## 6-2. TPM / RPM — 429의 진짜 원인, 숫자로 계산해보기

### 정의
- **TPM (Tokens Per Minute)**: 분당 처리 가능한 토큰 총량
- **RPM (Requests Per Minute)**: 분당 요청 건수

**중요**: Azure OpenAI는 요청을 받을 때 **출력 토큰을 미리 예약(max_tokens 기준)** 해서 계산한다. 그래서 `max_tokens`를 크게 잡아두면 실제로 짧게 답해도 쿼터를 크게 먹는다. **이걸 아는 사람은 드물다.**

### 실제 계산 — "20명이 왜 문제였나"를 숫자로 설명하기
```
가정:
  · 배포 쿼터: 60,000 TPM
  · 1회 진단 응답: 입력 3,000토큰(프롬프트+검색문서) + 출력 1,000토큰 = 4,000토큰
  · 사용자 20명이 동시에 진단 진행

1턴에 소모: 20명 × 4,000토큰 = 80,000토큰

→ 60,000 TPM 쿼터를 1턴 만에 초과!  ★
→ 429 발생

여기에 이미지 생성까지 겹치면:
  · 이미지 생성은 별도 쿼터(분당 이미지 수)를 씀
  · 산출물 1개당 이미지 3장 × 20명 = 60장이 순간에 몰림
  · 이미지 API는 RPM 한도가 낮은 편 → 즉시 429
```

> **면접 결정타 문장**: "'20명'이라는 숫자만 보면 작아 보이지만, **부하의 단위는 사용자 수가 아니라 분당 토큰과 요청 수**입니다. 1턴당 4,000토큰이면 20명이 동시에 진행할 때 분당 8만 토큰이 나가고, 쿼터가 6만이면 구조적으로 429가 날 수밖에 없습니다. 그래서 해결책도 '사용자를 줄이는 것'이 아니라 **'순간 요청량을 시간축으로 펴는 것'**(큐 + 동시성 제한)이었습니다."
> ↑ **주석판에서 지적한 '20명은 작은데요?' 지뢰에 대한 완전한 대답이다. 이 숫자 예시를 외워가라.**

## 6-3. 배포 유형 3종

| 유형 | 과금 | 특징 | 언제 |
|---|---|---|---|
| **Standard (종량제)** | 쓴 만큼 | 쿼터 공유, 트래픽 몰리면 429 | 개발·중소 트래픽 |
| **Provisioned (PTU)** | 시간당 고정 | 처리량을 **예약**. 다른 테넌트 영향 없음, 지연 안정적 | **운영 트래픽이 예측 가능하고 SLA가 필요할 때** |
| **Batch** | 종량 대비 저렴(약 절반) | 24시간 내 처리 보장, 즉시성 없음 | **야간 대량 요약·임베딩** |

> **면접 대비 2개**:
> - **"쿼터가 모자라면 PTU 검토 안 하셨나요?"** → "검토했지만 트래픽이 간헐적이라 시간당 고정 과금이 비효율이었습니다. 상시 부하가 예측 가능해지는 시점에 PTU가 맞다고 봤습니다."
> - **"요약 배치는 Batch API로 돌리면 되지 않나요?"** → **좋은 지적이라고 인정할 것.** "즉시성이 필요 없는 요약 작업이었으니 Batch API가 비용·쿼터 양쪽에서 더 나은 선택이었습니다. 당시엔 검토하지 못했고, 지금이라면 그렇게 했을 겁니다."

## 6-4. 모델 스위처 = 전략 패턴(Strategy Pattern)

```python
# 인터페이스로 추상화 (의존성 역전)
class LLMProvider(Protocol):
    async def generate(self, prompt: str) -> str: ...

class AzureGPT4o(LLMProvider): ...
class AzureGPT4oMini(LLMProvider): ...
class ClaudeProvider(LLMProvider): ...

# 런타임에 어드민 설정값을 보고 구현체를 고른다
def get_llm() -> LLMProvider:
    name = settings.get("active_llm")     # DB 또는 .env
    return REGISTRY[name]()
```

**설계 원리 이름표**:
- **전략 패턴** — 알고리즘(모델)을 런타임에 교체
- **의존성 역전 원칙(DIP)** — 상위 모듈이 구체 구현이 아니라 인터페이스에 의존
- **어댑터 패턴** — 벤더별 API 차이를 공통 인터페이스로 흡수

> **면접에서**: "서비스 계층 모듈화"라고 쓴 것을 **"LLM 프로바이더를 인터페이스로 추상화하고 런타임에 전략을 교체하는 구조"** 라고 바꿔 말하면 훨씬 정확하게 들린다.

## 6-5. 기능 플래그(.env 런타임 노브) — 정확히 알기

### 함정
```python
# 이렇게 쓰면 프로세스 시작 시 1회만 읽는다
IMAGE_CONCURRENCY = int(os.getenv("IMAGE_CONCURRENCY", "3"))   # 모듈 로드 시 확정
→ .env를 고쳐도 재기동 전엔 안 바뀜

# 이렇게 쓰면 매번 읽는다
def get_concurrency():
    return int(os.getenv("IMAGE_CONCURRENCY", "3"))            # 호출 시점에 읽음
→ 단, os.environ은 프로세스 시작 시 로드된 사본이라
   .env 파일을 고쳐도 반영되지 않는다 (dotenv를 다시 로드해야 함)
```

> **정확한 답변**: "`.env`는 컨테이너 기동 시 주입되는 값이라, 엄밀히는 **재배포는 없어도 재기동은 필요**했습니다. 코드 빌드·이미지 푸시 과정을 건너뛰니 반영이 분 단위로 짧아진 게 실질적 이득이었고, **진짜 무중단 동적 설정이 필요하면 Azure App Configuration이나 DB 기반 설정 테이블이 정답**입니다."
> ↑ **과장하지 않고 정확히 말하는 게 훨씬 강하다.**

### 기능 플래그의 4가지 용도 (알아두면 좋음)
```
① 릴리스 토글    — 미완성 기능을 배포하되 꺼둠
② 운영 토글      — 부하 시 선생성 끄기  ← 내가 쓴 용도
③ 실험 토글      — A/B 테스트
④ 권한 토글      — 특정 사용자에게만 노출
```

# 7장. 비동기와 성능 — 이벤트 루프의 실체

## 7-1. 동기 vs 비동기 — 그림으로

```
[동기 — 워커 1개가 요청 1개를 붙잡고 있음]
워커1: |──요청A 처리──|······LLM 응답 대기 5초······|──응답──|
                      ↑ 이 5초 동안 워커1은 아무것도 못 함(놀고 있음)
워커2: |──요청B 처리──|······대기 5초······|──응답──|

워커가 4개면 → 동시에 4명만 처리 가능. 5번째 사용자는 대기.

[비동기 — 워커 1개(이벤트 루프)가 여러 요청을 번갈아]
루프:  |A시작|B시작|C시작|D시작|...|A응답처리|B응답처리|...
        ↑ A가 대기에 들어가는 순간 B로 넘어감
        ↑ 대기 시간이 겹쳐진다(overlap)

워커 1개로도 → 수백 명 동시 처리 가능 (전부 "대기 중"이므로)
```

### 핵심 통찰
**비동기는 일을 빨리 하는 게 아니라, 노는 시간을 없애는 것이다.**
CPU 계산 자체는 하나도 빨라지지 않는다. **기다리는 시간이 대부분인 작업(LLM 호출, DB 조회, 외부 API)** 에서만 이득이다.

## 7-2. I/O bound vs CPU bound

```
[I/O bound]  시간의 대부분을 "기다리는" 데 씀
   예: LLM API 호출(5초 중 4.99초가 네트워크 대기), DB 조회, 파일 읽기
   → 비동기가 극적으로 효과 있음 ★

[CPU bound]  시간의 대부분을 "계산하는" 데 씀
   예: 이미지 리사이징, 대규모 정렬, 암호화 연산
   → 비동기는 효과 없음. 오히려 이벤트 루프를 막는다.
   → 별도 프로세스(multiprocessing)나 워커 큐로 빼야 함
```

**LLM 애플리케이션은 거의 전부 I/O bound다.** 그래서 FastAPI(async)가 자연스러운 선택이었다는 게 자소서의 논리다.

## 7-3. GIL (Global Interpreter Lock)

### 한 문장 정의
파이썬 인터프리터가 **한 번에 하나의 스레드만 파이썬 바이트코드를 실행**하게 만드는 잠금장치.

### 그래서 뭐가 되고 뭐가 안 되나
```
스레드 4개로 CPU 계산  → GIL 때문에 사실상 1개만 실행. 빨라지지 않음 ✗
스레드 4개로 I/O 대기  → 대기 중엔 GIL을 놓아준다. 병렬 대기 가능 ✓
asyncio               → 애초에 스레드 1개. 대기를 겹치는 방식 ✓
multiprocessing       → 프로세스가 각자 GIL을 가짐. 진짜 병렬 ✓
```

> **면접 문장**: "파이썬은 GIL 때문에 CPU 병렬은 안 되지만, LLM 호출처럼 I/O 대기가 지배적인 워크로드에선 asyncio만으로 충분한 동시성을 얻을 수 있습니다. **동시성(concurrency)과 병렬성(parallelism)은 다른 개념**이고, 저희가 필요했던 건 전자였습니다."

## 7-4. async에서 절대 하면 안 되는 것 ★실무 함정

```python
# ✗ 최악 — 이벤트 루프 전체가 5초간 멈춘다
@app.post("/chat")
async def chat():
    response = requests.post(AZURE_URL, ...)   # 동기 라이브러리!
    return response

# 이 5초 동안 다른 모든 사용자의 요청도 전부 멈춘다.
# 동기 서버보다 오히려 나빠진다.

# ✓ 올바름
async def chat():
    async with httpx.AsyncClient() as client:
        response = await client.post(AZURE_URL, ...)
    return response

# ✓ 동기 라이브러리를 꼭 써야 한다면 스레드풀로 밀어낸다
    result = await asyncio.to_thread(blocking_function, arg)
```

**같은 함정 목록**: `time.sleep()`(→`asyncio.sleep`), 동기 DB 드라이버(→`asyncpg`), `open()`으로 큰 파일 읽기, CPU 무거운 루프.

> **면접 질문**: "async 썼는데 왜 성능이 안 나오죠?" 라는 상황 질문이 나오면 → **위 목록을 순서대로 점검한다고 답하면 실무자로 인정받는다.**

## 7-5. 스트리밍과 TTFT

```
[스트리밍 없음]
사용자 클릭 ────────── 8초 침묵 ────────── 전체 답변 등장
                     ↑ 사용자는 "멈췄나?" 하고 이탈

[스트리밍 (SSE)]
사용자 클릭 ─ 0.5초 ─ "귀사의" → "제조업" → "특성상" → ... (토큰이 흘러나옴)
             ↑ TTFT (Time To First Token)
전체 완료까지는 여전히 8초지만, 체감 대기는 0.5초
```

**핵심**: 실제 지연(latency)을 못 줄이면 **체감 지연(perceived latency)** 을 줄여라. 자소서의 **선생성(Pre-commit) 토글**도 정확히 같은 발상이다.

# 8장. 부하 · 큐 · 재시도 — 3부의 이론적 배경

## 8-1. 큐 이론 기본 — Little's Law

### 공식
```
L = λ × W

L (Length)  : 시스템 안에 있는 평균 항목 수 (큐 길이)
λ (lambda)  : 평균 도착률 (초당 몇 건 들어오나)
W (Wait)    : 항목 하나가 시스템에 머무는 평균 시간
```

### 실제 계산으로 감 잡기
```
상황: 이미지 생성 요청이 초당 5건 도착(λ=5), 1건 처리에 2초(서비스 시간)

동시 처리 가능 수(동시성)를 c라 하면 처리율 μ = c / 2초

c=3 이면 μ = 1.5건/초  →  도착 5건/초 > 처리 1.5건/초
   → 초당 3.5건씩 큐에 쌓임 → 1분이면 210건 적체 → 무한 증가 ★
c=10이면 μ = 5건/초    →  겨우 균형 (하지만 429가 터짐)
c=20이면 μ = 10건/초   →  여유롭지만 429 폭증

★ 이게 자소서에서 말한 "낮추면 처리량↓, 높이면 429↑ 딜레마"의 정체다.
```

### 그래서 진짜 해법은?
```
도착률 λ를 우리가 못 줄이고, 처리율 μ는 외부 쿼터가 상한을 정한다면
→ 남은 선택지는 "시간축으로 펴는 것" 뿐이다.

  · 큐로 버퍼링 (버스트를 시간에 걸쳐 소화)
  · 선생성으로 한가할 때 미리 만들기 (λ를 시간축에 분산)
  · 우선순위로 중요한 것부터 (전체 처리량은 같아도 체감은 개선)
  · 그래도 안 되면 입구를 막는다 (백프레셔/admission control)
```

> **면접 문장**: "λ > μ면 큐는 이론적으로 무한히 자랍니다. 큐를 늘리는 건 해결이 아니라 **지연을 뒤로 미루는 것**이고, 결국 ①처리율을 올리거나 ②도착률을 시간축으로 펴거나 ③입구를 막거나 셋 중 하나여야 합니다. 저희는 쿼터 때문에 ①이 막혀 있어서 ②와 ③을 조합했습니다."

## 8-2. 포화점 (Knee Point)

```
처리량
  ↑
  │           ┌──────────────  ← 여기서부터 아무리 동시성을 올려도 처리량은 그대로
  │        ／                    (오히려 컨텍스트 스위칭/재시도로 떨어지기도)
  │     ／
  │  ／
  └──────────────────────────→ 동시성
           ↑ 포화점(knee)

지연
  ↑                        ／  ← 처리량은 안 느는데 지연만 폭증
  │                     ／
  │──────────────────                (429 재시도가 지연을 더 키움)
  └──────────────────────────→ 동시성
```

> **부하테스트의 목적은 "몇 명까지 되나"가 아니라 "포화점이 어디인가"를 찾는 것이다.** 이렇게 말하면 부하테스트를 제대로 이해한 사람으로 보인다.

## 8-3. 레이트 리밋 4종 — 그림으로

```
① 토큰 버킷 (Token Bucket)  ★버스트 허용
   ┌─────┐  물방울이 초당 5개씩 채워짐(rate)
   │ ●●● │  버킷 최대 10개(capacity)
   │ ●●● │  요청 1건 = 토큰 1개 소비
   └──┬──┘  토큰 없으면 거절/대기
      ↓
   특징: 놀다가 토큰이 가득 찬 상태면 순간 10건을 한 번에 통과시킬 수 있음
        → 버스트를 허용하면서 평균 속도는 제한

② 리키 버킷 (Leaky Bucket)  ★버스트 평탄화
   요청 →  ┌─────┐
           │ ▓▓▓ │  들어오는 건 몰려도
           └──┬──┘  나가는 건 항상 초당 5개 (구멍 크기가 고정)
              ↓ 일정 속도
   특징: 출력이 완벽히 균일 → "버스트 평탄화"는 정확히 이 효과 ★

③ 고정 윈도우 (Fixed Window)
   [00:00~00:59] 카운트 100까지 허용
   [01:00~01:59] 카운트 리셋
   함정: 00:59에 100건 + 01:00에 100건 = 1초 사이에 200건 통과 ★경계 문제

④ 슬라이딩 윈도우 (Sliding Window)
   "지금부터 과거 60초" 를 계속 이동하며 계산 → 경계 문제 없음
   비용: 요청 타임스탬프를 다 기억해야 함(로그 방식) 또는 근사 계산
```

> **자소서 연결**: "라운드로빈 우선순위 큐로 버스트를 평탄화"라고 썼는데, **평탄화의 이론적 정체가 리키 버킷**이다. 이 매핑을 말하면 좋다.

## 8-4. 재시도 — 잘못하면 장애를 키운다

### 나쁜 재시도가 만드는 재앙: Thundering Herd
```
00:00.0  API 장애 발생. 100건이 동시에 실패
00:01.0  100건이 "1초 후 재시도" → 동시에 100건 재요청 → 또 실패
00:02.0  또 동시에 100건 → 또 실패
→ 장애 중인 서버를 계속 두들겨서 복구를 방해한다 ★
→ 이걸 "재시도 폭풍(retry storm)"이라고 한다
```

### 올바른 재시도 3요소

```
① 지수 백오프 (Exponential Backoff)
   1회차: 1초 후   2회차: 2초 후   3회차: 4초 후   4회차: 8초 후
   → 실패가 계속되면 간격을 벌려 상대를 쉬게 한다

② 지터 (Jitter) — 무작위 편차 ★가장 자주 빠뜨리는 것
   백오프만 있으면 100건이 "정확히 동시에" 재시도한다(여전히 herd)

   Full Jitter (AWS 권장):
     대기시간 = random_between(0, min(최대치, base × 2^시도횟수))

   1회차: 0~1초 사이 랜덤   → 100건이 1초에 걸쳐 고르게 흩어짐 ★
   2회차: 0~2초 사이 랜덤
   3회차: 0~4초 사이 랜덤

③ 상한
   최대 재시도 N회 + 전체 데드라인(예: 30초 넘으면 포기하고 폴백)
   → 재시도가 사용자 대기를 무한정 늘리면 안 된다
```

### Retry-After를 존중한다는 것
```
HTTP/1.1 429 Too Many Requests
Retry-After: 12          ← 서버가 "12초 뒤에 오라"고 알려줌

→ 우리가 계산한 백오프(4초)보다 서버 말이 우선이다.
→ 서버는 자기 쿼터 리셋 시점을 알고 있으니 가장 정확하다.
→ 무시하고 4초 뒤에 때리면 또 429 (그리고 쿼터를 더 갉아먹음)
```

> **자소서의 "Retry-After 기반 재시도"는 이 부분을 정확히 한 것이다. 잘한 부분이니 자신 있게 말할 것.**

### 재시도하면 안 되는 것 구분
```
재시도 O:  429(레이트리밋), 500/502/503/504(서버 일시 오류), 타임아웃, 커넥션 리셋
재시도 X:  400(잘못된 요청 — 다시 보내도 똑같이 틀림), 401/403(인증), 404
           422(검증 실패), 콘텐츠 필터 차단
```

## 8-5. 멱등성 (Idempotency)

### 한 문장 정의
**같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같아야 한다**는 성질.

### 왜 재시도와 세트인가
```
클라이언트 → [이미지 생성 요청] → 서버 (이미지 생성 성공!)
클라이언트 ← ✗ 응답이 네트워크에서 유실 ←
클라이언트: "실패했네" → 재시도 → 이미지가 2장 생성됨 + 요금 2배 ★

해결: 멱등키
클라이언트 → [요청 + Idempotency-Key: abc123] → 서버
서버: "abc123 처리한 적 있나?" → 있으면 저장된 결과를 그대로 반환, 새로 만들지 않음
```

> **면접 대비**: "재시도했는데 이미지가 중복 생성되진 않았나요?" 라는 질문이 오면 → 멱등키 또는 "요청 ID 기준 중복 체크"로 답한다. 없었다면 "중복 생성 가능성이 있었고, 멱등키를 뒀어야 했다"고 인정.

## 8-6. 공정 큐잉 — HOL Blocking을 숫자로

### Head-of-Line Blocking (선두 차단)
```
[단순 FIFO 큐]
큐: [A1][A2][A3][A4][A5][A6][A7][A8][A9][A10][B1][C1]
     └──── 사용자 A가 한꺼번에 던진 10건 ────┘  ↑    ↑
                                          사용자B  사용자C

처리 속도가 초당 1건이면:
  A는 1~10초에 완료
  B는 11초에 완료   ← A 때문에 10초를 기다림
  C는 12초에 완료   ← 단 1건 요청했는데 12초 대기 ★불공정
```

### 라운드로빈 공정 큐잉
```
[사용자별 큐를 두고 번갈아 하나씩]
A큐: [A1][A2][A3]...[A10]
B큐: [B1]
C큐: [C1]

처리 순서: A1, B1, C1, A2, A3, A4, ...
  B는 2초에 완료  ★
  C는 3초에 완료  ★
  A는 여전히 12초에 전부 완료 (A 입장에선 손해가 거의 없음)

→ 전체 처리량은 동일한데 다수 사용자의 체감이 극적으로 개선된다.
```

### 2계층 구조 (내 시스템)
```
우선순위 1 (즉시)   : 사용자가 방금 클릭한 요청
                      └ 이 안에서는 사용자별 라운드로빈 (공정성)
우선순위 2 (배경)   : 선생성(Pre-commit) 작업
                      └ 우선순위 1이 비어있을 때만 처리

→ 부하가 높으면 선생성이 자연히 굶는다 = 자원이 실사용자에게 자동 재배분됨 ★
→ 이게 "선생성이 429를 유발하지 않나요?"에 대한 완벽한 답이다.
```

### 기아(Starvation)와 에이징(Aging)
```
문제: 우선순위 2가 영원히 처리 안 될 수 있음
해결: 대기 시간이 길어지면 우선순위를 승급시킨다(aging)
      priority = base_priority - (대기시간 / 10초)
```

## 8-7. 백프레셔 (Backpressure)

### 비유
**수도관에 물이 너무 많이 들어오면, 밸브를 잠가 상류에 "그만 보내"라고 신호를 보내는 것.**

```
[백프레셔 없음]
요청 무한 수용 → 큐 100만 건 → 메모리 폭발 → 서버 다운
                              또는 모든 응답이 10분 지연 → 사실상 장애

[백프레셔 있음]
큐 길이 > 임계값(예: 500) 이면
  → 새 요청에 즉시 503 + Retry-After 응답
  → 또는 사용자에게 "지금 혼잡합니다. 대기하시겠습니까?" 표시

★ 핵심 인식: "요청을 거절하는 것"이 "모두를 느리게 만드는 것"보다 낫다.
   빠른 실패(fail fast)가 느린 성공보다 사용자에게 친절할 때가 많다.
```

## 8-8. p95 / p99 — 평균이 거짓말하는 이유

```
10건의 응답시간: 1, 1, 1, 1, 1, 1, 1, 1, 1, 51 (초)

평균 = 6초        ← "6초면 그럭저럭이네" (거짓말)
p50(중앙값) = 1초  ← 절반은 1초
p90 = 1초
p99 ≈ 51초        ← 100명 중 1명은 51초를 기다린다 ★

현실: 그 1명이 이탈하고, 그 1명이 컴플레인을 넣는다.
```

**정의**: p95 = "요청의 95%가 이 시간 안에 끝난다"는 값. 상위 5%의 느린 요청은 이보다 느리다.

> **면접 문장**: "평균 응답시간은 꼬리(tail latency)를 감춥니다. 저희는 어드민에 [평균/p95 중 실제로 본 것]을 봤는데, 부하 상황에서 문제가 되는 건 항상 p95 이상 구간이라 **평균만 보면 개선 효과를 잘못 판단**하게 됩니다."

## 8-9. DB 커넥션 풀 — 왜 크게 잡으면 안 되나

```
PostgreSQL의 특징: 커넥션 1개 = OS 프로세스 1개 (스레드가 아님!)
  → 커넥션 200개 = 프로세스 200개 = 메모리·컨텍스트 스위칭 부담

처리량
  ↑        ┌───┐
  │      ／     ＼____      ← 어느 지점을 넘으면 오히려 떨어진다
  │   ／
  └──────────────────→ 커넥션 수
        ↑ 최적점 (보통 CPU 코어 수의 2~4배 수준)

계산 감각:
  워커 프로세스 4개 × 풀 사이즈 10 = 40 커넥션
  + 배치 스케줄러 5
  = 45  ≤  postgres max_connections (기본 100)  ✓

★ 워커를 늘리면 커넥션이 곱하기로 늘어난다는 걸 잊으면 사고가 난다.
```

**PgBouncer**: 애플리케이션과 DB 사이에 두는 커넥션 풀러. 앱에서 온 수백 개의 논리적 커넥션을 실제 DB 커넥션 수십 개로 다중화한다. 커넥션이 병목이면 정석 해법.

**증상별 진단**:
```
"QueuePool limit reached, timeout"  → 풀이 부족하거나, 커넥션을 안 반납하는 코드가 있음
"too many connections for role"      → DB의 max_connections 초과
응답은 되는데 느림                   → 풀 대기가 지연에 포함됨. p95를 보면 드러남
```

## 9-2. k-익명성 — 왜 필요한가

```
"이름을 지웠으니 익명이다"는 착각이다.

익명화했다는 데이터:
  나이 34 / 성별 남 / 우편번호 06234 / 직업 보험계리사

→ 이 조합에 해당하는 사람이 세상에 1명뿐이라면? 완벽히 식별된다.
  (실제로 미국 인구의 87%가 [생년월일+성별+우편번호]만으로 식별 가능하다는
   유명한 연구가 있다)

k-익명성: 어떤 속성 조합으로도 최소 k명이 똑같이 보이도록 일반화
  나이 34 → 30대
  우편번호 06234 → 062**
  → 같은 조합인 사람이 5명 이상(k=5)이 되도록

l-다양성: k명이 모여도 그들의 민감정보(병명 등)가 전부 같으면 뚫린다
         → 민감값도 l개 이상 다양해야 함
t-근접성: 그 분포가 전체 분포와 비슷해야 함
```

> **면접에서 한 줄**: "식별자를 지우는 것과 비식별화는 다릅니다. **준식별자(나이·성별·지역)의 조합으로 재식별이 가능**하기 때문에, k-익명성 같은 기준으로 검증해야 진짜 비식별입니다."

## 9-3. JWT 해부

```
실제 토큰:  eyJhbGciOi...  .  eyJzdWIiOiI...  .  SflKxwRJSMe...
            └── Header ──┘    └── Payload ──┘   └─ Signature ─┘

Header  {"alg": "HS256", "typ": "JWT"}
Payload {"sub": "user123", "exp": 1735689600, "role": "admin"}
Signature = HMAC-SHA256( base64(Header) + "." + base64(Payload), 비밀키 )
```

### 핵심 3가지 (이거 모르면 위험)
```
① Payload는 암호화가 아니라 Base64 인코딩이다
   → 누구나 디코딩해서 읽을 수 있다 (jwt.io에 붙여넣으면 바로 보인다)
   → 주민번호, 전화번호 같은 걸 넣으면 안 된다 ★

② 서명은 "위조 방지"이지 "내용 감추기"가 아니다
   → 내용을 바꾸면 서명이 안 맞아서 검증 실패 (위조는 막힘)
   → 하지만 읽는 건 막지 못함

③ 서버가 상태를 안 갖는 게 장점이자 단점
   장점: DB 조회 없이 검증 가능 → 확장성
   단점: 발급된 토큰을 즉시 무효화할 수 없다 ★
        → "로그아웃했는데 토큰이 아직 유효한" 문제
        → 대응: 짧은 만료(15분) + refresh token, 또는 블랙리스트(상태를 다시 가짐)
```

### HS256 vs RS256
```
HS256 (대칭): 발급자와 검증자가 같은 비밀키를 공유
              → 서비스가 하나면 충분. 키가 여러 곳에 퍼지면 위험

RS256 (비대칭): 발급자만 개인키, 검증자들은 공개키
              → 마이크로서비스 여러 개가 검증해야 하면 필수 ★
```

### 저장 위치 딜레마 (실제로 나오는 질문)
```
localStorage:  XSS 공격에 취약 (스크립트가 읽을 수 있음)
httpOnly 쿠키: XSS엔 안전하지만 CSRF 대비 필요 (SameSite 속성 설정)
메모리(변수):  가장 안전하지만 새로고침하면 사라짐

→ 정답은 없고 트레이드오프. "어디에 뒀고 그 위험을 어떻게 인지했는지"를 말하면 된다.
```

## 9-4. 망분리와 Private Endpoint

### 왜 금융권은 망을 분리하나
```
[일반 기업]
사내 PC ──── 인터넷 ──── 외부 서비스
        하나의 네트워크

[금융권 전통 망분리]
업무망(내부망)              인터넷망
 · 고객정보 시스템           · 웹서핑, 메일
 · 계정계                    · 외부 API
    ↕ 물리적/논리적 분리 (자료 전송은 망연계 솔루션으로만)

→ 외부에서 침투해도 고객정보에 도달할 수 없다
→ 문제: 생성형 AI는 대부분 인터넷 저편의 API다. 업무망에서 못 부른다. ★
```

### Private Endpoint가 푸는 문제
```
[퍼블릭 엔드포인트]
우리 서버 ── 공용 인터넷 ── api.openai.azure.com
              ↑ 트래픽이 인터넷을 지나감

[Private Endpoint]
우리 VNet
 ├ 앱 서버
 └ 프라이빗 엔드포인트(사설 IP) ══ Azure 백본망 ══ Azure OpenAI
                                    ↑ 인터넷을 거치지 않음 ★
 + 해당 리소스의 퍼블릭 액세스는 차단
 → "논리적 폐쇄망" 구성
```

**함께 나오는 것들**: VNet(가상 네트워크), NSG(네트워크 보안 그룹 = 방화벽 규칙), Private DNS Zone(프라이빗 IP로 이름 해석), Service Endpoint(Private Endpoint보다 약한 방식), **Managed Identity**(키 없이 Azure 리소스 간 인증 → `.env`에 키를 두지 않아도 됨).

> **최신 동향으로 언급하면 좋은 것**: 금융위가 2024년에 **금융권 망분리 개선 로드맵**을 내놓으면서 생성형 AI 활용을 위한 규제 샌드박스·단계적 완화가 논의됐다. *(면접 직전에 최신 상태를 한 번 확인하고 들어갈 것 — 규제는 계속 바뀐다.)*

# 10장. AI 거버넌스 — 설명가능성, 편향, 모델 리스크

## 10-1. 설명가능성 두 종류 — 혼동하면 위험

```
[전통 XAI]  대상: 예측 모델(신용점수, 사기탐지, 이탈예측)
  질문: "왜 이 사람의 대출이 거절됐나?"
  답:   SHAP로 각 피처의 기여도를 계산
        연소득 -0.31 / 기존대출 -0.28 / 근속연수 +0.12 / ...
  → 모델 내부를 수학적으로 분해한다

[생성형 AI의 근거 제시]  대상: LLM 답변
  질문: "왜 이렇게 답했나?"
  답:   ...LLM 내부 가중치를 SHAP로 설명하는 건 사실상 불가능하다 ★
  → 대신: "이 답변은 [약관 제12조]와 [사례 #1123]에 근거했다"고 출처를 제시
  → 모델을 설명하는 게 아니라, 근거를 추적 가능하게 만든다
```

> **이 구분을 말하는 게 이 문항의 핵심이다**:
> "LLM은 수십억 파라미터의 확률 계산이라 SHAP 같은 방식으로 내부를 설명하기 어렵습니다. 그래서 **모델의 설명가능성 대신 프로세스의 추적가능성**으로 접근해야 합니다. 어떤 문서를 근거로 삼았고, 어떤 프롬프트 버전이 쓰였고, 어느 단계에서 사람이 개입했는지를 전부 기록하는 방향입니다."

### SHAP 간단히 (물어볼 수 있으니)
```
게임이론의 Shapley value에서 왔다.
"이 피처가 있을 때와 없을 때 예측이 얼마나 달라지는가"를
가능한 모든 피처 조합에 대해 평균낸 값 = 그 피처의 기여도

장점: 이론적 근거가 탄탄, 전역/국소 설명 모두 가능
단점: 계산 비용이 큼 (근사 알고리즘 사용)

LIME: 예측 지점 주변만 단순한 모델로 근사해서 설명. 빠르지만 국소적.
```

## 10-2. Citation의 3단계와 함정

```
[1단계] 문서 단위 출처
   "출처: 자동차보험 약관"
   → 함정: 약관이 200페이지면 검증이 불가능하다. 사실상 알리바이용.

[2단계] 문장 단위 인용 + 위치
   "지급 기한은 30일입니다 [약관 제12조 2항, p.45]"
   → 사람이 확인 가능. 실무 최소 기준.

[3단계] 사후 검증 (Attribution / Faithfulness Check)
   생성된 답변의 각 주장에 대해:
     "이 문장이 인용된 근거에 실제로 포함되어 있는가?"를
     별도 모델(NLI 모델 또는 LLM)로 판정
   → 근거에 없으면 답변을 차단하거나 경고 표시
   → RAGAS의 faithfulness가 이걸 자동화한 것
```

> **면접 핵심 질문**: "Citation을 붙였는데 그 출처가 실제로 답변을 뒷받침하는지는 어떻게 보장하나요?"
> **답**: "출처를 붙이는 것과 근거가 되는 것은 다릅니다. LLM이 문서를 참조했다고 표시해도 실제 내용은 다르게 요약할 수 있어서, **답변 문장과 근거 문장의 함의 관계를 사후 검증**하는 단계가 필요합니다. 금융이면 이 검증을 통과 못 한 답변은 사용자에게 내보내지 않는 게 맞다고 봅니다."

## 10-3. 편향과 공정성 — 4/5 룰 계산해보기

```
상황: AI가 보조하는 보험 인수심사

              신청자 수    승인 수    승인율
남성 그룹        1,000       800      80%
여성 그룹        1,000       560      56%

Disparate Impact Ratio = 56% / 80% = 0.70

4/5 룰(80% 룰): 비율이 0.8 미만이면 차별 소지 있음
→ 0.70 < 0.8  → ★ 문제 있음. 원인 분석 필요.
```

### 공정성 지표 3종 (동시 만족 불가능하다는 게 유명한 결과)
```
Demographic Parity  : 집단별 승인율이 같아야 한다
                      → 실제 위험도가 다르면 오히려 불합리할 수 있음

Equal Opportunity   : 실제 자격이 있는 사람 중 승인율이 같아야 한다 (TPR 동일)

Equalized Odds      : TPR과 FPR이 모두 같아야 한다

★ 이 셋은 수학적으로 동시에 만족될 수 없다(불가능성 정리).
  → "무엇을 공정으로 볼 것인가"는 기술 문제가 아니라 정책 결정이다.
```

### Proxy 변수 — 가장 실무적인 함정
```
성별을 입력에서 제거했다 → 공정한가?

  직업: 간호사, 유치원교사 → 여성 비율 높음
  가입채널: 특정 앱        → 연령대 편중
  거주지: 특정 지역        → 소득/인종 상관

→ 모델이 이런 대리 변수로 성별·연령을 "간접적으로 학습"한다
→ 보호속성을 지우는 것만으론 부족하고, 결과를 모니터링해야 한다 ★
```

> **면접 문장**: "보호속성을 입력에서 빼는 것만으로는 공정성이 확보되지 않습니다. 직업·거주지 같은 **대리변수를 통해 간접 차별이 발생**할 수 있어서, 입력 통제가 아니라 **출력 분포 모니터링**이 필요합니다. Fairlearn 같은 도구로 집단별 지표를 정기 측정하는 체계가 실질적이라고 봅니다."

## 10-4. 모델 리스크 관리 — 금융권 프로세스

```
① 모델 인벤토리
   사내 모든 AI/모델을 목록화: 목적, 소유자, 데이터, 리스크 등급, 최종 검증일
   → "우리 회사에 AI가 몇 개 돌고 있나요?"에 답할 수 있는 게 출발점

② 개발과 검증의 분리 (★금융권 핵심 원칙)
   만든 사람이 검증하면 안 된다.
   독립된 모델검증 조직이 가정·데이터·성능·한계를 재검토

③ 승인 및 배포
   변경관리 절차: 요청 → 검토 → 승인 → 배포 → 사후검증

④ 지속 모니터링
   성능 지표 추적, 드리프트 감시, 이상 탐지

⑤ 주기적 재검증
   연 1회 등 정기적으로 처음부터 다시 검증
```

### 드리프트 두 종류
```
Data Drift (입력 분포 변화)
  예: 코로나 이후 청구 유형 분포가 완전히 바뀜
  탐지: 입력 피처의 분포를 과거와 비교 (KS 검정, PSI 지표)

Concept Drift (입력-정답 관계 변화)
  예: 같은 조건인데 규정이 바뀌어 판정 결과가 달라짐
  탐지: 실제 결과(label)가 나오면 성능 지표 추적
  → 라벨이 늦게 나오는 도메인(보험금 심사)에선 탐지가 어렵다 ★

LLM에서의 드리프트:
  · 벤더가 모델을 업데이트해서 같은 프롬프트의 출력이 달라짐 ("silent update")
  · 대응: 모델 버전 고정(pinning) + 골든셋 회귀 평가
```

> **면접 대비 질문**: "모델이나 프롬프트를 바꿨을 때 품질이 떨어진 걸 어떻게 아나요?"
> **답**: "골든셋 기반 회귀 평가입니다. 프롬프트도 코드처럼 버전을 관리하고, 변경 PR이 올라오면 CI에서 50~100건의 골든셋을 돌려 faithfulness와 형식 준수율을 비교하는 구조가 필요합니다. **벤더가 모델을 조용히 업데이트하는 경우도 있어서 정기 스모크 평가도 같이 돌려야 합니다.**"

## 10-5. Human-in-the-loop 설계

```
자동화 수준 3단계
  in-the-loop     : 사람이 승인해야 실행됨       ← 보험 지급 심사는 최소 이 수준
  on-the-loop     : AI가 실행하되 사람이 감시·개입 가능
  in-command      : 사람이 전체 통제, AI는 조언만

설계할 때 정해야 할 것 4가지:
  ① 언제 게이트를 거나?     금액 임계값, 모델 신뢰도, 예외 유형
  ② 무엇을 보여주나?        답변 + 근거 문서 + 신뢰도 + 유사 과거 사례
  ③ 검토 결과를 어떻게 쓰나? 승인/반려 이력을 평가 데이터로 축적 ★
  ④ 자동 승인 비율 목표는?   100% 검토는 자동화 의미가 없다. 저위험만 자동.
```

> **주의할 함정 — 자동화 편향(Automation Bias)**: 사람이 검토한다고 해도 AI가 제시한 답을 그냥 승인하는 경향이 생긴다. **"검토했다"는 형식만 남고 실질 통제가 사라진다.** 이 리스크를 언급하면 매우 인상적이다. 대응은 신뢰도 낮은 건에만 게이트를 걸어 검토자의 주의를 집중시키기, 근거를 먼저 보여주고 AI 결론은 나중에 보여주기 등.

## 10-6. 프롬프트를 자산으로 관리한다는 것

```
프롬프트 = 코드다. 그러면 코드에 하는 걸 다 해야 한다.

버전 관리    : v1, v2, v3 ... 언제 누가 왜 바꿨는지
스테이징     : dev → staging → prod 승격
롤백         : prod 라벨을 이전 버전으로 되돌리기 (즉시)
리뷰/승인    : 변경 시 2인 승인(4-eyes)
테스트       : 골든셋 회귀 평가 통과해야 승격
추적성       : ★응답 로그에 prompt_version을 남긴다
              → "이 답변은 어떤 프롬프트에서 나왔나"를 사후에 알 수 있어야 감사 대응 가능
```

> **가장 중요한 한 줄**: "**응답 로그에 프롬프트 버전, 모델 버전, 검색된 문서 ID를 함께 남기는 것**이 사후 감사의 최소 요건입니다. 이게 없으면 6개월 뒤에 문제가 생겼을 때 원인을 재구성할 수 없습니다."

### 내가 한 방식의 약점 (선제적으로 인정할 것)
```
내가 한 것: DB + 어드민에서 현업이 프롬프트를 직접 편집
장점: 현업이 즉시 개선 가능, 개발자 병목 없음
약점: 코드 리뷰·승인 절차가 없다. 누가 언제 왜 바꿨는지 추적이 약할 수 있다.
      잘못 바꾸면 즉시 프로덕션에 반영된다.

→ 금융권 버전: 편집(현업) / 검토(리스크) / 승인(책임자) / 배포(자동)를 분리하고
   스테이징에서 평가를 통과해야 프로덕션으로 승격되는 구조
```

## 12-4. 모르는 게 나왔을 때 (외워둘 3단 대응)

```
1) 되묻기      "저희는 그걸 ○○라고 불렀는데, 말씀하신 게 △△가 맞을까요?"
2) 이어붙이기  "직접 써보진 않았지만, 제가 만든 ○○가 같은 문제를 다루는 걸로 이해합니다."
3) 정직        "그건 제대로 모릅니다. 다만 왜 필요한지는 알 것 같은데, 설명해주시면 배우겠습니다."

★ 절대 금지: 아는 척하고 틀리기.
  용어를 모르는 건 감점이 작지만, 틀린 설명은 신뢰를 통째로 날린다.
```

---

## 마지막 — 이 문서를 쓴 이유

자소서에 적힌 표현들은 대부분 **결과**를 말한다. "구조화했다", "최적화했다", "개선했다".
면접관이 궁금한 건 **그 밑의 판단**이다. 왜 그 구조여야 했고, 무엇과 무엇 사이에서 골랐고, 무엇을 포기했는지.

이 문서의 모든 챕터는 결국 하나의 질문에 답하기 위한 것이다 —
**"그래서, 왜 그렇게 하셨어요?"**

용어를 외우는 게 아니라 **트레이드오프를 말할 수 있게 되는 것**이 목표다.
모르는 걸 만나면 정직하게, 아는 건 근거와 함께. 그거면 충분하다.
